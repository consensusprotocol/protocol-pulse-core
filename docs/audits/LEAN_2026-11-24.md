## (1) The lock settles the clips' words before any line-up is judged (`7124d705f`)

**The issue was as GPT stated it.** In package.py at 88ffce7b6, line 4564 asked the clips-alone verdict and 4672-4701
then asked the lock and re-judged corrected words. Build 171's 8b5ec831 ("bitcoins" corrected to "bitcoiners") is the
case. The second ear had already heard "Bitcoiners" at 17:59:21, at the pool stage, which sent it to the lock
(ruling 143). Its line-up was still judged on "bitcoins" at 18:07:55.

**What changed (lean):**
- package.py:4534, `lock_first`: for each angle, before its join table, the lock is asked for the angle's own clips, the
  hook first so it is asked as the hook, in one request.
- An answer already on file is used only for the exact span, transcript text, role, trim and rules/decoder
  (`lock_precheck.answer`, unchanged).
- A held clip is out before any verdict is paid.
- A corrected clip is judged again on its words once, by its own gates (package.py:4482, `rejudge_heard`'s clips-only
  mode): step A on both families, exclusion, the second pass and the OUT edge, plus rating and vision for the hook
  only. It then takes its original's place.
- No verdict changes nothing.
- At the line-up, if the lock's answer is the one the line-up was judged on (`lock_settled`, package.py:4599/4862),
  nothing is judged again. The no-voice path works the same way.

**Tests:** `python3 -B -m pytest -q tests/package/test_lean_lock_first.py`: **6 passed**. On the base code 5 fail
because it has no `lean`; the lock-cache test passes there, as it should.
- Positive: the lock is asked before the first verdict. There is one clips-alone verdict, and it is on "FTX". Step A
  runs on the corrected clip twice, once each family. The pin seals FTX with the correction named.
- Must-fail: a clip the lock holds never reaches a judged line-up, while the old path judges it first. A corrected clip
  that fails its own gates is out before any line-up. A lock answer is never reused across text, span, role, trim or
  rules.
- The old path, as a contrast: two verdicts.

## (2) A clip whose thought runs on: extended, re-anchored or shortened, inside bounds (`f2a284f56`, fixed in `275499e30`)

**The issue was as GPT stated it.** In out_edge.py at 88ffce7b6, lines 161-172 gave no extension target for a window
record or a clip cut inside a sentence. Lines 270-271 refused such clips even when the following sentence was right
there. Build 171's CoinTelegraph 16473cca is the case: a window record whose checker named "It's not boring then." as
the sentence that finishes it, refused.

**What changed (lean, `recover=True`):**
- out_edge.py:152, `around`: one target per sentence the checker read, aligned with the texts. A window record counts
  too, as does the clip's own cut sentence's end (the OUT edge re-anchored). The window record's last sentence never
  counts, because the decode window may have cut it.
- out_edge.py:223: a cached verdict answers the very same question (the key is unchanged), and its targets are read from
  the source again.
- out_edge.py:299: an out-of-range answer is refused, where before it raised an IndexError.
- out_edge.py:337: otherwise the clip is shortened once, to its previous sentence (`tail_variant.variant`), and kept only
  at 8 s (SHORT_CLIP_S) or more. Otherwise it is refused.
- tail_variant.py:68, `extend`: may re-anchor inside the last sentence; the IN edge stays a sentence start.
- package.py:3886: every new span goes through `admit` (the pool's rules and 20 s clip, step A, the second recogniser)
  and, on the lean path, the exclusion screen's free part on its own words. Then it is asked the question on its own
  edge; no answer is UNVERIFIED, never a pass.
- **Fixed in `275499e30`, found by the offline replay below.** 16473cca's real extension got no answer from step A
  (HELD) and was filed as REFUSED, but no answer is never a refusal. On the lean path, an `admit` that fails for want
  of an answer now leaves the clip UNVERIFIED (open work, asked again next build), and it is not shortened for that
  (out_edge.py `NO_VERDICT`).
- Also fixed there, on both paths: `build()` now keeps the never-empty pass's out-edge record
  (`never_empty.soft_record.out_edge`). `outcomes.undone` read that pass's unverified clips as open work from this key,
  but the record never carried it.

**The bounds, and why:**
- Only the 3 sentences the checker read, because a later one was never judged.
- Never a window record's last sentence, for the decode reason above.
- The existing 20 s clip.
- One shortening, because each new span costs a paid step A and a second ear.

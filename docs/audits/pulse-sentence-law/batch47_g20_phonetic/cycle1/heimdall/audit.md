## Raised but not agreed
- qwen27b:F1 [critical] Phonetic matching is vulnerable to false positives for short names or names with empty Metaphone codes. The logic `if _dm_codes(a) else a == b` allows a match if the name token has no code (e.g., numbers or symbols) and the transcript token is identical, OR if they share a code. However, Double Metaphone often produces short or identical codes for distinct words (e.g., 'C' and 'K' both map to 'K', 'S' and 'Z' to 'S'). More critically, if a name token is a single letter or a number that maps to an empty code, it requires exact equality. But if it maps to a code, it only requires intersection. For a name like 'A B', if 'A' maps to 'A' and 'B' maps to 'B', it might match 'A C' if 'C' also maps to 'B' (unlikely) or more realistically, short codes like 'K' for 'K' and 'C' allow 'K' to match 'C'. The ruling requires 'every token matches phonetically'. The implementation uses set intersection. If a name token has multiple codes and a transcript token has multiple codes, any overlap suffices. This is standard for Metaphone, but the risk is that 'Stephan' (STFN) and 'Steven' (STFN) match, which is intended. However, 'Livera' (LFR) and 'Lubka' (LPK) do not match, which is intended. The flaw is in the handling of tokens with no code. If a name token is '1' (no code), it requires `a == b`. If the transcript has '1', it matches. This is correct. But consider a name 'I' (no code) and transcript 'I'. It matches. Consider 'I' and 'Y'. 'I' has no code, so it requires 'I' == 'Y', which is false. So it fails. This seems safe. However, the real issue is that `_dm_codes` returns a set. If the name token is 'C' (code 'K') and the transcript token is 'K' (code 'K'), they match. This is a phonetic match. The ruling says 'stefan lavera' vs 'Stephan Livera' must match. 'stefan' -> STFN, 'Stephan' -> STFN. 'lavera' -> LFR, 'Livera' -> LFR. They match. 'Steven' -> STFN, 'Lubka' -> LPK. 'Stephan' (STFN) matches 'Steven' (STFN), but 'Livera' (LFR) does not match 'Lubka' (LPK). So the whole name fails. This is correct. The potential defect is if a name has a token that maps to a very common code, like 'S' (S) or 'K' (K). For example, 'S' vs 'Z'. 'S' -> S, 'Z' -> S. They match. Is 'S' phonetically equivalent to 'Z'? In Metaphone, yes. The ruling says 'phonetically (double-metaphone or equivalent)'. So this is compliant. I will look for a different defect. (agree: 1)
- qwen27b:F2 [high] The review drop logic uses `G.spoken_channels(script, reg, credited)` to verify the script names every credited channel. This call does NOT pass `phonetic=True`. This is correct per the ruling ('the strict pre-render reading, never phonetic'). However, `spoken_channels` with `phonetic=False` (default) only uses exact and ratio matching. The ratio matching uses `SequenceMatcher` with a threshold of `G20_NAME_RATIO` (0.85). If the script contains a name that is slightly misspelled but within 0.85 ratio, it will be considered 'named'. The ruling says 'the sign-off SCRIPT names every credited channel'. It does not explicitly forbid fuzzy matching in the script check, but it says 'strict pre-render reading'. The original `spoken_channels` docstring says 'A CREDITED channel may match fuzzily...'. So the script check allows fuzzy matching. This might be a defect if 'strict' implies exact. However, the code comment says 'the strict pre-render reading, never phonetic'. It does not say 'never fuzzy'. So this is likely compliant. I will look for a clearer defect. (agree: 1)
- qwen27b:F3 [medium] The `_phonetic_span` function returns a span based on the start and end positions of the tokens in the *normalized* transcript string `t` (which is `"".join(ttoks)`). However, the `starts` list is built by accumulating `len(tok)` for each token in `ttoks`. This is correct for the normalized string. The span is then used in `spoken_channels` to check for overlaps and to extract the `heard` string. The `heard` string is `t[span[0]:span[1]]`. This is the normalized substring. This is correct. I will look for a defect in the overlap check. (agree: 1)
- glm:F1 [medium] Phonetic route can hear a credited name via a shared Double Metaphone code even when the transcript token is unrelated, because the match is 'any shared code' (DM primary/secondary), not 'same primary code'; short/empty-code tokens also fall back to exact equality only, so a single-token credited name with a short code (len<4 skip applies only to the exact/ratio routes, not phonetic) can match a wrong short token. Evidence: `if all((_dm_codes(a) & _dm_codes(b)) if _dm_codes(a) else a == b for a, b in zip(ntoks, win))` — intersection of primary+secondary codes means e.g. 'Stephan' (STFN/STFN) vs 'Steven' (STFN/STFN) would match, but the ruling only excludes 'Steven Lubka' vs 'Stephan Livera' via the second token; a credited name whose every token shares a secondary code with a different name passes. Also, when `_dm_codes(a)` is empty the token must be equal, but a token with codes where the transcript token has none (b has no codes) yields an empty intersection and fails — asymmetric handling is intended, yet a 1-token window in a long transcript can align 'stefan' with any STFN-adjacent token. Fix: require the primary codes to be equal (or both primary and secondary), and skip the phonetic route when any name token has no code. (agree: 0)

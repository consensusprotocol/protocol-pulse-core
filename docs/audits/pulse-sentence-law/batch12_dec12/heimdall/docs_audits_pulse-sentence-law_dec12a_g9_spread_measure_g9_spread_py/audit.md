## Consensus findings (majority of panel agrees)
- **[medium] docs/audits/pulse-sentence-law/dec12a_g9_spread/measure_g9_spread.py:82** Silent skip of missing real finals underestimates the re-encode spread, producing a G9 floor that is not derived from the full measurement. If the absent final would have carried an extreme tail-luma, the spread is too small, the floor is too high, and a tail that should fail G9 passes — a fail-open path.
  - evidence: `if not os.path.exists(p):
            continue`
  - fix: Replace the silent `continue` with a hard failure (e.g. `sys.exit(f"missing final: {p}")`) so the script cannot emit a spread.json computed over a subset of the required finals. The spec mandates 'the real finals' as part of the measurement set; an incomplete set invalidates the floor.
  - raised by qwen27b:F1; agree: deepseek, qwen27b

## Raised but not agreed
- qwen27b:F2 [low] The 1e-9 epsilon in the round-up is too small to absorb IEEE-754 representation error in `spread * 100`. For a spread that is an exact multiple of 0.01 (e.g. 0.04), `0.04 * 100` evaluates to 4.000000000000001; subtracting 1e-9 does not bring it back to 4.0, so `ceil` returns 5 and the spread is rounded to 0.05 instead of 0.04. The error is conservative (floor is 0.01 lower than intended) but the published spread_rounded does not match the spec's 'rounded up to 0.01' for exact multiples. (agree: 0)

## Added in cross-examination (not voted on)
- deepseek: [medium] `setparams=colorspace=bt709` only tags the stream; it does not convert YUV from BT.601 to BT.709. For untagged finals, the luma is still decoded as BT.601, so the measurement does not match G9's BT.709 decoding.
- deepseek: [medium] Pre-rounding the spread to 4 decimals before rounding up to 0.01 can cause under-rounding. For example, a true spread of 0.04001 becomes 0.04, then rounds up to 0.04 instead of the required 0.05.

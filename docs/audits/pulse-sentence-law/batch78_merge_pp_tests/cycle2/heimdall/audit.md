## Raised but not agreed
- qwen27b:F1 [critical] The code still hard-codes the absolute path to the main tree's key loader file (`/home/ultron/protocol_pulse/video_pipeline_v3/relay.py`). The audit requirement was to remove hard-coded key-file paths and rely on the pipeline's loader. While `relay.py` is a loader, hard-coding its absolute path in a test file violates the 'no key-file path parsed in a test directory' constraint and makes the test non-portable. More critically, the new test `test_keys_are_read_only_by_name_through_the_pipelines_loader` in `test_f0_cpu_guard.py` asserts `FB.KEY_LOADER == "/home/ultron/protocol_pulse/video_pipeline_v3/relay.py"`. This creates a circular dependency where the test passes only because the code hard-codes the exact string the test expects, rather than verifying the behavior of using a dynamic loader. If the path changes, the test fails, but the intent was to avoid hard-coding paths entirely. (agree: 1)
- qwen27b:F2 [high] The test `test_keys_are_read_only_by_name_through_the_pipelines_loader` scans for string constants ending in `.env` or containing `/.env`. However, the new code in `frontier_blind.py` uses `KEY_LOADER` which ends in `.py`, not `.env`. The test's assertion `assert FB.KEY_LOADER == "/home/ultron/protocol_pulse/video_pipeline_v3/relay.py"` is a static check that does not verify the *behavior* of `_key` (i.e., that it actually calls `get_key` and doesn't parse a file). The check `".get_key" in src and "open(" not in src` is fragile: if `relay.py` itself uses `open()` (which it likely does to read the key file), the test doesn't catch that `frontier_blind` is indirectly allowing file access. More importantly, the test passes for the wrong reason: it asserts the source code contains `.get_key` and does not contain `open(`, but `frontier_blind._key` does not call `open(` directly; it calls `spec.loader.exec_module(mod)`. The absence of `open(` in `frontier_blind.py` is trivially true and doesn't prove the key isn't read from a file by the loaded module. The test should verify that `_key` returns a value from the environment or a known source, not just that the source code lacks `open(`. (agree: 0)
- glm:F1 [medium] The new key-file test asserts on the fixture (hard-coded absolute path) rather than the behaviour, and its 'no key file named' scan is self-fulfilling: the only key path in the suite is spelled apart ('.' + 'env') so the scan can never see it, and the assertion FB.KEY_LOADER == '/home/ultron/protocol_pulse/video_pipeline_v3/relay.py' just re-states the constant it claims to verify — the test can only fail if the constant is edited, not if the loader stops being the pipeline's (e.g. a copied relay.py next to the test would still pass, since only os.path.isfile is checked, not that it is the main tree's copy). (agree: 1)
- glm:F2 [low] test_the_runner_refuses_every_call_of_the_suites_list can pass for the wrong reason: it builds `expected` from a hard-coded tuple ('pinned here, not read from the list') while the probe reads the names from netguard_names. If a name is later added to the shared list, the probe prints it, names gains an extra element, and the equality assert fails — good — but if a name is REMOVED from the list, the probe prints fewer names and the test still passes as long as the remaining ones match, so the 'every call of the list' property is only half-pinned; the len(names) < 9 control also silently passes a 9-name list that dropped, say, getnameinfo and duplicated another. (agree: 1)
- glm:F3 [low] The toy gate's module-level _calls = [0] counter makes the gethostbyaddr/getnameinfo alternation depend on import order and case count, and the test's coverage assertion only requires BOTH names to appear somewhere in the rows; with 33 rows it holds, but if the corpus shrinks to an odd count the last case's call is deterministic yet the test's set-equality (== {"gethostbyaddr", "getnameinfo"}) would fail for a reason unrelated to the guard (a fixture/corpus-size coupling, not the behaviour under test). (agree: 0)

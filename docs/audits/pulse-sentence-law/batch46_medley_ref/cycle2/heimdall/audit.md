## Raised but not agreed
- qwen27b:F1 [high] The flow check compares the current code's `pulse_transitions.plan` output against the junctions parsed from the frozen `render_*.log` files. This violates the requirement that flow inputs be checked against the EDL's segments and not driven by the reference. If the reference log contains a junction that the current code no longer produces (or vice versa), the check will fail, but more critically, it uses the reference's output as the ground truth for the plan, rather than verifying the plan against the EDL's structural constraints. The spec states: 'flow and layout inputs checked against the EDL's segments (not driven by the reference)'. Here, the *expected* junctions are driven by the reference log. (agree: 1)
- qwen27b:F2 [medium] The cut check uses `sentence_law.write_lock_cut_table` on a scratch copy of the EDL. However, `write_lock_cut_table` likely depends on the `cuts_final.json` or similar reference data to determine the 'lock' or 'hop' boundaries. If the function uses the reference's `cuts_final.json` as input to generate the table, then the check is circular: it compares the output of a function fed by the reference against the reference itself. The spec says 'reproduces the decisions with the CURRENT code on the reference's frozen files'. If `write_lock_cut_table` reads `cuts_final.json` from the scratch dir (which is a copy of the reference), it is not reproducing the decision from the EDL/transcripts alone, but rather validating the reference against itself. (agree: 0)
- glm:F1 [high] The PIN/EDL segment pairing is by position, not by video_id: the zip pairs segments before the video_id check, so a PIN whose segments are reordered but whose first segment happens to match the EDL's first segment passes the pairing check for that segment while later segments are silently compared against the wrong reference locks. The consensus requires pairing by video_id. (agree: 0)
- glm:F2 [medium] The flow check compares the plan's junctions against the render log, but the plan is built from the reference's own TRANSITIONS.json style and the log's style word is only checked against that same reference value; a changed decision that alters the style in the EDL (and hence what the plan would place) while the reference TRANSITIONS.json still says the old style passes, because the log's style word is compared to the reference, not to what the current code would choose. (agree: 1)

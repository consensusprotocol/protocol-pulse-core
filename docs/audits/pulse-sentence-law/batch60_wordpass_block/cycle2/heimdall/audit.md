# Heimdall audit

**Question:** Batch 60 cycle 2 (verification). Cycle 1: one consensus [medium] (started fetches keep asking YouTube during a block): implemented with a per-cycle hold event set by the first sign-in failure in its own thread (CONSENSUS.md); the GPU part deliberately not (no platform request; re-downloads would cost more).

Batch 60 = the word-pass worker under a platform block (the integrator's own worker; no orchestrator ruling changes).
Background: pipeline/word_pass_worker.py turns ranked ledger moments into sentence-ready window word records on GPU1. Each cycle picks up to 120 moments the rows file has no row for (passed_ids), downloads each video's audio once (transcript_store.download_audio: yt-dlp with data/yt_cookies.txt), cuts windows, decodes them under the GPU1 lease, and appends ONE row per moment (ready, not ready, or failed with its error). A moment with a row is never worked again. On 2026-11-13 at 04:47 ET YouTube began refusing EVERY request from this machine ("Sign in to confirm you're not a bot. Use --cookies-from-browser or --cookies for the authentication"): 330 moments got permanent failure rows in 2 minutes (each download fails fast, so the cycles spun), and a metadata probe on a known-public video failed the same way. An age-gated or sign-in-only VIDEO produces the same sign-in wording, so the wording alone cannot say whose failure it is.
The change:
- BLOCK = the sign-in wording; blocked_failure(why) = an 'acquisition:' failure (download or metadata) in that wording.
- control_ok(): ONE metadata request (the store's own ts._ytdlp: same cookies) for CONTROL_VIDEO (the approved medley reference's public source); True only when yt-dlp exits 0 and prints its id; any exception or failure is False.
- cycle(): a blocked_failure triggers control_ok() at most once per cycle. Control refused -> the platform's failure: no row is written for it (blocked_rows counts it), the fetches not yet started are cancelled (a cancelled fetch writes no row either), report['blocked'] states why, and main() sleeps before the next cycle. Control answered -> that video's own failure: written as before with control_ok: true. Every other failure: written exactly as before, and the control is never asked.
- passed_ids(): a blocked_failure row WITHOUT control_ok does not count (so the 330 rows written during the block are retried once; if they fail again while the control answers, they are written with control_ok and stay done).
Tests (6 new in test_word_pass_worker.py; the 20 old pass): a blocked cycle writes nothing, asks the control once, and the next cycle writes every moment; a video's own sign-in failure is written with control_ok and not picked again; old rows: only a sign-in acquisition row without control_ok is retried; a non-sign-in failure never asks the control; control_ok's call and its False cases; main() sleeps after a blocked cycle.
FIND: anything still open; a moment lost (a row written) because of the platform; more than a handful of requests per blocked cycle; a video's own permanent failure retried forever; a race in the hold event or the futures handling; a test that does not test what it claims. Only state what you can verify from the diff. Reply with the JSON verdict; keep the reasoning short; at most 3 findings.

## Raised but not agreed
- glm:F1 [medium] After a platform block, the control verdict is cached for the whole cycle, so a fetch that already started before the block and finishes later with a sign-in failure is counted as the platform's (blocked_rows, no row) even though the control was never asked for it — but worse, if the control answered (control_ok true) for the first failure, later sign-in failures in the same cycle are written with control_ok: true even though the control was asked once, before those failures, which is the intended design; the real defect is the opposite branch: when the control answers, hold.clear() runs on every subsequent sign-in failure, so a fetch that started before the first failure (hold not yet set) is unaffected, but a fetch that started after the first failure was skipped via hold and its SKIPPED rows are counted in blocked_rows while the control answered — those moments are silently dropped from this cycle's report counts (neither written nor failed) and only recovered by the next cycle, which is by design; the actual defect: verdict['control_ok'] is only set when the FIRST sign-in failure occurs, so if the first sign-in failure's control check returns True, hold.clear() lets later fetches proceed, but if a later fetch's failure arrives while verdict already says control_ok, the control is never re-asked — acceptable. The verifiable defect: when the control answers, hold.clear() is executed inside the per-failure loop, so it runs once per sign-in failure, but a fetch thread that passed the hold.is_set() check just before hold.set() races the setter and proceeds to make requests during a block. (agree: 1)

## Added in cross-examination (not voted on)

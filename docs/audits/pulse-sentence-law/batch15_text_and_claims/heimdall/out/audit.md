# Heimdall audit

**Question:** Batch 15 (2026-11-12) for three pipeline defects found in a fresh editorial run, all fail-closed but costing real coverage. (1) E-FAIL-036 / law L-h: YouTube caption transcript records keep HTML entities ('S&amp;P', '&gt;&gt;'); (2) E-FAIL-037: word-level Whisper records join split tokens with spaces ('$81 ,000', 'U .S.', '$1 .3 billion'), so verbatim evidence quotes never matched the stored text. Fix: transcript_store.read_text = html.unescape + remove whitespace before a '.' or ',' that continues a word (regex \s+(?=[.,][0-9A-Za-z])); every chunk's text is built through it (stored immutable records are never rewritten; their hashes are checked on read); story_semantics._norm (quote verification) decodes entities; the embedding cache file name gets '.t2' so vectors match the read text. (3) E-FAIL-038 / law L-i: query derivation re-read two channel-cluster claims as other events (an election claim became 'the US held its elections on November 8th', an invented date; a $74K claim became a Schwab listing from the label summary). Fix: derive_story_query for origin=='transcript_cluster' passes CLUSTER_NOTE instead of the label summary and sets underlying_event to the claim verbatim (the model's reading kept as underlying_event_derived); wire items are byte-identical. Unchanged: quote_in's verbatim requirement, the adjudicator and support prompts, all thresholds. Find: correctness bugs, any way a quote that was NOT spoken could now verify (false accept through read_text or _norm), regex over-joins of real words, entity decoding that could enable prompt injection (quote_data is applied to excerpts in prompts), cache inconsistencies, and tests that do not test what they claim. At most 6 findings, quote evidence.

## Raised but not agreed
- qwen27b:F1 [medium] _norm decodes HTML entities but does NOT apply the split-token regex, creating an asymmetry with read_text. If any code path passes raw (unprocessed) transcript text to quote_in, entity quotes will match (via html.unescape in _norm) but split-token quotes ('$81 ,000') will still fail because _norm has no _SPLIT_TOKEN equivalent. The test itself proves this gap: quote_in(quote, [raw]) is False while quote_in(quote, [ts.read_text(raw)]) is True. The fix only works when every text reaching quote_in has already passed through read_text; _norm's entity decoding gives a false sense that both issues are handled at the verification layer. (agree: 0)
- qwen27b:F2 [medium] For transcript_cluster items, underlying_event is set to item.get("headline") which can be None if the key is absent or null. Downstream consumers that expect a string (e.g., prompt formatting, storage, or comparison) will receive None and may raise TypeError or silently produce a broken record. The model's own underlying_event (a validated string) is discarded in favour of a potentially-None field. (agree: 0)
- qwen27b:F3 [low] TestEmbeddingCacheVersion.test_vectors_are_cached_under_the_decoded_text_version only asserts the cache file name ends with '.t2.npz'. It mocks encode to return np.ones, so it never verifies that the vectors stored in the .npz were actually computed on entity-decoded / split-token-joined text. A regression that writes raw-text vectors under the .t2 name would pass this test. (agree: 0)
- qwen27b:F4 [low] The regex \s+(?=[.,][0-9A-Za-z]) removes whitespace before a period or comma followed by an alphanumeric. In the (rare but possible) case where a speaker says two separate numbers and Whisper inserts a space before the period—e.g. 'I scored 99 . 100' meaning '99 out of 100'—the regex joins them to '99.100', silently altering the meaning. The test only covers the intended split-token cases and a benign sentence boundary, not this over-join. (agree: 0)
- qwen27b:F5 [low] html.unescape in _norm changes the normalisation of entity-like substrings compared to the old code. Old _norm('&amp;') → 'amp' (the letters a,m,p survive the [^a-z0-9 ] filter). New _norm('&amp;') → html.unescape → '&' → '' (empty string). An empty normalised quote is a substring of every text, so quote_in('&', [any_text]) would return True—a false accept. While a one-character quote is unlikely in practice, the same applies to any quote consisting solely of characters that unescape to non-alphanumerics (e.g. '&gt;&lt;' → '<>' → ''). (agree: 0)

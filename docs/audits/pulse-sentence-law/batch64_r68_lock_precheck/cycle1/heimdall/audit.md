## Consensus findings (majority of panel agrees)
- **[medium] pipeline/lock_precheck.py:0** A reused entry is answered from the last non-error entry keyed only by span+window+approved_text, but the entry's role is overwritten and the reused entry's role is taken from the new request, so two requests differing only in role (or in trimmed_leading/untrimmed_start, which are not part of the reuse key) silently get the earlier answer even though the lock (make_lock's source label, trimmed_lock's i0/i1) depends on them.
  - evidence: `prev = latest(vid, s["start"], s["end"], sha, (lo, hi), s.get("approved_text"))

    entry = dict(prev, request_id=r["request_id"], role=s["role"], r`
  - fix: Include role and trimmed_leading/untrimmed_start in the reuse key (or recompute the lock from the cached acquisition instead of copying the previous entry).

## Raised but not agreed
- qwen27b:F1 [critical] GPU0 lease is not acquired when all requests are cached, violating the 'render always first' discipline and potentially allowing the pre-check to run concurrently with a render or without yielding. (agree: 1)
- qwen27b:F2 [high] The `decode` function checks `LJ.render_wants_gpu0()` inside the loop, but if a render requests GPU0 mid-decode, it returns `None` and leaves the `decoded` dict incomplete. The subsequent `answer` call for that request will use `dec.get(vid, (None, 'not decoded', 0.0))`, resulting in an 'error' outcome for all segments, even if some were successfully decoded. This is a partial failure that is not clearly distinguished from a total failure. (agree: 0)
- qwen27b:F3 [medium] The `latest` function uses `e['window'] == want` for comparison, where `want` is a list of floats. If the window values in the entry are stored as integers or have floating-point precision differences, this comparison may fail, leading to stale reuse or missed cache hits. (agree: 0)
- qwen27b:F4 [low] The test `test_a_render_comes_first` sets `self.wants.side_effect = [False, False, True]` to simulate a render requesting GPU0 while the lease is being taken. However, the `gpu0.lease` mock is a `contextlib.nullcontext()`, which does not actually check the yield flag. The test relies on the `decode` function checking `LJ.render_wants_gpu0()` inside the loop, but the lease acquisition itself is not tested for yield flag compliance. (agree: 1)
- glm:F2 [low] The reuse key compares the stored window list to floats built from the request, but the stored window comes from the same computation, so a request whose video's other segments changed (same span, different line-up) gets a fresh window and correctly misses — yet the result file is keyed only by span+sha, so entries for different windows accumulate in one file and latest() filters by window; correct, but the reuse check in _cached uses window(r["segments"], vid) which for a single-segment request defaults to (start, end) — the same span sent alone after being sent in a line-up is NOT reused (a second decode, second spend) even though the ruling says 'an identical span + window + approved text under the same sha is answered from its last non-error entry'. (agree: 1)
- glm:F3 [low] In serve_once, when a render asks while the lease is held (decode returns None), the finally clause calls gpu0.release_all() and the lease context exits, but the requests already decoded stay in `decoded` and are answered — while the ones not yet decoded stay pending; however the requests that WERE decoded are answered after the lease, and their locks (with the paid second recogniser) run outside the lease, which the ruling permits ('the locks and the second recogniser (network) run after it is left'). No defect; noted for completeness. (agree: 1)

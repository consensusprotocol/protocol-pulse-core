### [P1] F1 — `medley_trace`'s `elif` chain: `ratings` is consulted before `second_pass`/`trim_cut`/`hook_onset`, so a stale failure row can be masked by a rating, and the correctness rests on undocumented record semantics
Lines 119–154. The chain order is `unusable → no_role → ad → reposted → failed → ratings → second(≠PASS) → trim_cut → onset(≠PASS) → onset+hp.error → onset → 3-channel → pool`. Because `ratings` wins over the prescreen dicts, a moment present in both `hook_pool.ratings` and, say, `prescreen.trim_cut` (FAIL) is placed at stage 5/6. That is right **only if** `package.build` guarantees: (a) `trim_cut` holds failures only, (b) `second_pass`/`hook_onset` hold outcome maps whose PASS rows are later overwritten by ratings, and (c) a rating is written only for a moment that actually opened. None of these three invariants is stated in the driver's docstring, and the test at 549–553 *bakes them in* (`t: 3` from a trim_cut FAIL while `t` also has an onset PASS; `x: 3` "cannot open" while `x` has an onset PASS — so `onset` holds PASS rows too, meaning `trim_cut`-before-`onset` ordering is load-bearing). If any invariant breaks (a retried moment whose prescreen dict keeps the old FAIL while ratings got the new entry), the funnel counts a "rated" moment that the record says never opened — and the funnel is the deliverable of part (1). Fix: one docstring line per dict stating failure-only vs outcome, or check the later stages first / assert consistency. Severity: P1 because the whole diagnosis rests on these semantics being true of `package.build`'s writers, and the driver cites the producing lines (:2617/:2643/:2666) but never states the semantics it assumes.

### [P2] F2 — `spotlight_trace`'s step-A detection is prose-matching on `out`
Line 173: `stepa = st == 0 and (str(why).startswith("step A") or "no verdict (law L-m)" in str(why))`. Stage-0 stops are free screens *unless* they are step A's; the driver distinguishes them by the wording of a free-text field. The tests pin both strings (571–572), good, but the coupling is to prose, not to a structured field. ### [P2] F3 — `funnel`'s tie rule keeps the *latest* build's reason, but `best[k]` compares only stages, so a *lower*-stage later record also overwrites... no — it doesn't; but the *stage-0 vs stage-1* mixing in `spotlight_trace` can downgrade a moment across builds
Line 194: `if k not in best or c[0] >= best[k][0]` — a tie keeps the latest, correct per the spec. But because `spotlight_trace` takes the **max** stage per moment *within* a build (line 176: `if k not in out or c[0] > out[k][0]`), while `medley_trace` takes the *single* `elif`-chain verdict, the two paths contribute differently: a moment that the medley stopped at stage 1 and the spotlight stopped at stage 0 in the *same* build gets the medley's stage (max), fine. However, in `funnel` the fold across builds uses `>=`, so a later build's *equal-stage* record replaces the reason even if the later record is from the *other path* — meaning the reported "why" may come from the spotlight when the medley's reason was the editorially relevant one. Not wrong (the spec says "a tie keeps the LATEST build's reason" and doesn't distinguish paths), but the report's `furthest[k]["why"]` can silently switch provenance between paths. P2: record which path supplied the reason, or note it.

### [P2] F4 — `hook_pass`'s `called` heuristic: `cost > 0 or seconds_hook >= 1` — a genuinely free/0-second call is classed "no model call"

### [P2] F5 — `near_misses`' "held back" counts `scroll`/`alone` at exactly 3, but a moment held at 3 by *two* parts (scroll 3, alone 3) is counted once per part, and `setup <= 3` uses `<=` while the others use `==`
Lines 301–306. `if r.get(p) == 3: held[p] += 1` for scroll/alone, but `if isinstance(r.get("setup"), int) and r["setup"] <= 3: held["setup..."] += 1`. A setup of 2 (or 1) counts as "held back by setup" though the rating is `min(scroll, alone)` and setup is *not in the rating* — the label admits it ("not in the own-job rating since ruling 61"), so counting any setup ≤ 3 as a *cause* of the 3 is arguably wrong: a moment with scroll 3, alone 5, setup 1 is held by scroll, not by setup. The report line (440–441) presents these as "held back by", which a reader will read causally. P2: either count setup only when it *would* have changed the ruling-61 rating (i.e. `min(scroll, alone) == 3` and `setup == 3`... which is the same as the others), or rename the key. Also: a moment with both scroll=3 and alone=3 increments both counters, so `sum(held.values())` can exceed `threes` — the report's phrasing "held back by X" invites a part-to-blame reading that the counts don't support. Test at 611–612 pins the doubled counting, so it's intended; still, the *causal* presentation is the defect.

### [P2] F6 — `all_ratings`' spotlight completion: `by_id` keys are split on `":"` — a moment id containing `:` (or a cache key with more than one colon) misattributes cache records

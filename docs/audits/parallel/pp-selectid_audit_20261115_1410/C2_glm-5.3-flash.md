## 3. NEW FINDINGS FROM THIS REVIEW

**[P2] `_live_bar`'s minute-bucket cache can serve a bar that expired mid-build for up to 60 s — and the docstring admits it, but the *first* read of a build is not forced.** package.py:418-429. The cache key is `(mtime_ns, minute)`. Within one minute and one mtime, every caller shares one verdict. Consider the sequence: the calibration is written at 18:07:52; a build starts at 19:07:51 (23:59:59 old — valid) and reads the bar into `_LIVE` under key `(T, 19:07)`. The build runs past 19:08. At 19:08:00 the key changes, the bar is re-read, now 24h+1s old → `None` → every subsequent `hook_own` fails closed. That's the *intended* behaviour and the test at test_hook_bar.py:1127-1150 proves it. But note the corollary: a build that reads the bar at 19:07:59.9, forms its line-ups on it, and seals at 19:08:0.1, seals on a bar that its own `hook_pool` line says is valid while `hook_bar_mark()` (line 432-438, called at seal time, line 623-624) now reports "no valid hook calibration: no hook passes" in the very same package record. The package's `hook_pool.bar` and its `hook_bar.bar` mark can disagree. Both are honest records of when they were taken; the pin carries the *mark's* text. Not wrong — but the Telegram note could say "no valid hook calibration: no hook passes" for a package whose hooks were, in fact, judged on a then-valid bar. [P2]: have `hook_bar_mark()` fall back to the `hook_pool`'s recorded bar, or record both, or accept and document the 1-in-1440 race. Severity: cosmetic-to-misleading, no gate affected (the gates were judged earlier and correctly).

**[P2] `hook_ratings`'s `listed`-filter changes what "cached" means for the *replay* path, and the stand-in-router escape hatch is untested for the `AttributeError` branch.** package.py:344-347. The try catches `(AttributeError, P.ProviderError)`. The Canned test routers in test_medley.py:1378-1386 *do* define `chain` (a lambda), so the `AttributeError` branch — a router with no `chain` method at all — is exercised only by whatever production routers exist. `Router.chain` exists in providers.py:794, so the AttributeError branch is dead code in practice unless a future router drops it. That's fine, but the *ProviderError* branch is the interesting one: `router.chain` raises when the role/kind has no list. With ruling 115's Grok-only lists in all three routings, when is that possible? Only if `model_providers.json` loses the `coherence_verdict:hook` key in some future routing — at which point `listed = None` silently restores the *old* serve-anything-from-cache behaviour, exactly what glm's fix was meant to eliminate. A missing key should arguably fail closed (no list → no rating → no hook, L-m), not fall back to "any cached rating answers". [P2]: consider `listed = set(router.chain(...))` without the fallback, or log when the fallback engages. One line either way.

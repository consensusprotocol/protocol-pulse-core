## 3. NEW FINDINGS FROM THIS REVIEW

Things the combined Cycle 1 analysis did not surface:

**N1 (P2) — `reseal_attested.py:275`: the story_id rewrite assumes the pin's story_id *ends* with `-8hex`.**
`re.sub(r"-[0-9a-f]{8}$", "-" + sha[:8], pin["story_id"])`. If a future pin's story_id does not end in exactly 8 lowercase hex (e.g. an uppercase-hex or 12-hex suffix, or no suffix at all), the sub silently does nothing and the re-sealed pin keeps the *old* story_id while carrying a *new* package_sha256 — the story_id↔sha8 coupling the test asserts (`"moments-ledger_20261113_183302-" + sha[:8]`) breaks without any error. Fail-soft, not fail-closed. Concrete scenario: a pin whose story_id was built by a different naming convention (the diff shows only this one pin's convention). Mitigation: assert the sub actually replaced (compare before/after) or raise if `re.sub` returns the input unchanged. Nobody flagged this in Cycle 1.

**N2 (P2) — `reseal_attested.py:257-258`: the "no line quotes the changed words" gate reads only `edl_vo.bridges[].text`, `edl_vo.intro`, `title`, `caption` — it never looks at the segment's own `approved_text` (correct, that's what's changing) but also never at any takeaway/`gates`-adjacent free-text field.**
The ruling says "The takeaway, title and caption are re-gated only if they quote the changed words." The code's `lines` list is bridges + intro + title + caption. If the ruling's "takeaway" is a *separate* field from the bridges' texts (the ruling names "takeaway, title and caption" as three things; the code treats bridges' texts as the takeaway), a takeaway stored elsewhere (e.g. `mp["takeaway"]` or inside `gates` metadata) would silently skip the quote check. I cannot verify from this diff whether `edl_vo.bridges[].text` *is* the takeaway — the ruling's wording suggests it might be a distinct field. If it is distinct, this is a silent under-check (fail-soft: a quoting takeaway would carry over un-re-gated, violating the ruling's "re-gated only if they quote" — actually it would *skip* the re-gate, which the ruling permits only when it does NOT quote). Worth a one-line confirmation against the pin's actual schema; the dry run says "no line quotes the changed words" for this pin, so it's moot here but not for the next.

**N3 (P2) — `attest.py:73`: `critical()` is called with `texts = (run_t, pin_t)` — the *full* clip texts — but the ruling's L-v 2 name-detection is positional (mid-sentence).**
For a *short* difference at the very start of the clip, a capitalised first word of the *clip* is "not mid-sentence" in both texts, so `critical` returns False for it — consistent with the render (R2), so not a bug, but note the corollary: a name that opens the *clip* but is mid-sentence in the *render's full-clip decode* (the render's lock sees the full clip, this tool sees only words 32-73) could classify differently. Concretely: if the held span starts mid-sentence and the first differing token is a capitalised name, the render's `_lv2_critical` (full-clip context) might see it as mid-sentence (critical) while this tool's `critical` (span-only context) sees it as clip-opening (not critical) → class "function word" if it's in FUNCTION_WORDS, or None → refused (fail closed). Since FUNCTION_WORDS contains no capitalised-only entries and canon presumably lowercases, the practical divergence window is: a name that is (a) capitalised, (b) mid-sentence in the full clip, (c) at the very start of the held span, and (d) in FUNCTION_WORDS — essentially impossible (function words aren't names). So: theoretical, P2, and fail-closed in the only direction that matters (None → refuse). Nobody caught this.

**N4 (P2, informational) — `reseal_attested.py:216`: the seal-recompute check uses `mp.get("signoff_expected")` and `mp.get("btc_screen")` (the `.get`-with-None-arg pattern), matching the integrator's call.** Consistent with the test_speakers fix; no action. Listed only because nobody said it out loud in Cycle 1: the reseal tool's seal() call signature is now the 7-arg form, so the "attested" key entering SEALED_LATER is the *only* behavioural delta for the integrator's check, and it's guarded by "only when a segment carries it."

**N5 (P2) — `attest.py:147`: `quotes()`'s `has()` uses `range(len(t) - n + 1)` — when `n > len(t)` the range is empty (correct, returns False via the `any`), and when `n == 0` the guard `n > 0` returns False.** Both edges are handled. But the *neighbour* padding `p[max(c-1, 0):d+1]` means a difference at position 0 of the approved text is searched with only its right neighbour — a line quoting just that one changed token plus its right neighbour still hits; a line quoting the changed token *plus its (nonexistent) left neighbour* cannot. That's the intended "one neighbour on each side" semantics, consistent with `reads()`. No action; noted for completeness.

None of N1–N5 rises to P1: every one fails closed or is test-only, and the held pin's dry run exercises none of them.

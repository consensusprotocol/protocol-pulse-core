## Answers to the questions

**(a) Can a WRONG speaker name reach a pin?**
- Title-names-guest-while-host-speaks: only if the model's *basis* is 3+ words found in the clip/around it. If the basis is genuinely from the transcript, the name is evidence-backed; if the model picks the guest's name with a basis that's actually the host's words, code cannot tell (it only checks the basis's *presence*, not *whose* words they are). So yes, a wrong-but-evidence-adjacent name can reach the pin — this is inherent to one-call attribution and the order permits it ("never guess" is enforced only as far as the basis-verbatim check goes). Verified: `check` (line 222) tests presence, not ownership.
- A quote not in the text: rejected → "unknown" (line 222-224, test lines 696-700). ✓
- A person the source does not name: dropped from `people` (line 208-211, test 670-678); if they're also the proposed speaker, → "unknown" with why (line 220-221). ✓
- A reply out of contract: `check` raises → caught → "unknown, measured=False" (line 245-248, test 718-723). ✓

**(b) Silent failure / counted as pass?** No. Every failure path in `attribute` returns `name="unknown"`, `measured=False`, with a `why` (lines 234-248). `speaker_problems` accepts `measured: False` + "unknown" — that's the order's intent, not a silent pass. The one caveat: a *missing* `measured` key fails (P2-6, third case) — good, fail-closed. And `attribute_package` has no per-segment error isolation beyond what `attribute` itself catches (P1-1).

**(c) Inside the seal?** Yes. `seal()` adds `"speaker": s.get("speaker")` to the hashed body (line 41), and `to_pin` copies it onto the pin segment (line 81). `test_the_speaker_is_inside_the_seal` (lines 755-764) proves both directions: same record → same hash; changed name → different hash. ✓. `to_pin` refuses: no record, empty/whitespace name, missing/non-list `people`, non-bool `measured`, named-without-line, named-without-basis (lines 49-62 + test 746-753). It does *not* refuse: a named speaker absent from `people`, a `line` that isn't a source line, or extra/missing `backend`/`replayed` — those are weaker than `check()`'s guarantees (P1-3, downgraded P2).

**(d) Delivered/kept spans out, render clock?** `build` stamps `now = datetime.now(timezone.utc)` (line 342) before `PK.build` and records it as `as_of` — the render clock, per ruling 1, is the build's responsibility and the diff passes it via `E.Context(now, ...)` (line 343). Whether `PK.build`/`package.usable` honour `delivered` and `ctx.now` correctly is **not verifiable from this diff** (P1-4). What the diff does: it computes `delivered = delivered_pins(...) + package_spans(a.exclude)` before anything is written (lines 419-426, fail-closed on unreadable inputs), passes it to `PK.build`, and records `delivered_spans=delivered` in the result. The `--avoid-videos` filter (line 344) is applied to the moments *before* the build, and the fallback ("a second build without the avoidance") is a manual, separate invocation — the diff does not automate it, matching the docstring.

**(e) Do the tests fail on the defect each names?** Checked case-by-case:
- `test_a_person_stands_only_on_a_source_line...` — would fail if `check` accepted a non-source line (the "Saifedean Ammous" case) or a line that doesn't name the person (the "Natalie Brunell" case). ✓
- `test_a_speaker_is_named_only_on_a_basis...` — fails if the basis-verbatim check is dropped (the "As I said on my own podcast yesterday" case in the next test also covers invented quotes). ✓
- `test_a_title_that_names_a_guest...` — fails if source lines were accepted as their own basis. ✓
- `test_a_reply_out_of_contract...` — fails if a non-JSON reply produced a name or `measured=True`, or if `reject` weren't called. ✓
- `test_no_source_lines_or_no_word_record...` — fails if a call were paid when there's nothing to ask. ✓
- `test_the_pin_refuses...` — fails if `speaker_problems` misses any of the five malformed shapes. ✓ (note the third case, `{"name": "unknown", "people": []}`, is caught by the missing-`measured` branch, not the name branch — the test still fails correctly if the *measured* check were dropped, but it would then also need the `people`-missing case to fail; as written, `{"name": "unknown", "people": []}` without `measured` exercises the measured branch. If someone deleted the measured-bool check, this case would pass `to_pin` — wait: would it? `{"name": "unknown", "people": []}` — name ok, people is a list, measured missing → if the measured check were deleted, no problem → no PinRefused → test fails. ✓, the test does guard the measured check, just via this case.)
- `test_the_speaker_is_inside_the_seal` — fails if `seal` dropped the speaker field (the changed-name→different-hash assertion). ✓
- Fixture updates in `test_medley`/`test_angles` — they exist so `to_pin` doesn't newly refuse old paths; they'd fail if `speaker_problems` were stricter than the fixtures. They do not test that the *real* flow attaches records (that's `proof_*`'s job, untested offline). Noted.

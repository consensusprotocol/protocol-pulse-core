## F1 HIGH: pipeline/oracle/providers.py call_backend (diff 1342-1357), BACKENDS heimdall-* (1188-1193), available (1270); pipeline/oracle/ab.py run_role/_one (190, 207-214)
- Defect: Spend-guard hole. A back-end with no price table never passes Ledger.allow, so Heimdall calls are still made when SPEND.jsonl is at or over the 60 USD cap; their gateway-reported cost is only added afterwards. In the A/B pool the 90 % credit tripwire is read once before the batch, not 'before each call' as the providers docstring says, so a whole batch on three Heimdall back-ends runs with neither guard. `if credits and ...` also skips the tripwire when total_credits is 0.
- Evidence: `worst = ledger.allow(price, llm.est_tokens(system, user), b["max_tokens"], name) if price else 0.0`; the three heimdall-* back-ends declare no "price". ab.run_role calls `PV.available(...)` once per back-end, then every item goes straight to `PV.call_backend(name, ...)` in an 8-thread pool. available(): `if credits and used >= HEIMDALL_NOTIFY_AT * credits`.
- Fix: Call ledger.allow for every remote back-end: give Heimdall models a conservative worst-case price, and refuse when spent() >= cap even for unpriced calls. Re-check the Heimdall counter inside call_backend (under _heimdall_lock) rather than only in available(). Treat credits <= 0 as unavailable.

## F3 MEDIUM: pipeline/oracle/providers.py call_backend (diff 1343-1357); pipeline/oracle/llm.py Ledger (834-864)
- Defect: The reservation is released before the measured cost is written. Between release() and record(), a concurrent allow() from the A/B pool or the oracle/witness pools sees the finished call neither as reserved nor as spent, and can admit a call that takes the ledger past the cap. A call that raises after the vendor billed it is never recorded at all. _reserved is per Ledger instance, so two CLI processes sharing SPEND.jsonl do not see each other's in-flight calls.
- Evidence: `finally: if price: ledger.release(worst)` ... then later `ledger.record(**row)`. Ledger docstring: 'a call's worst case stays reserved while it is in flight, so concurrent calls can never pass the cap together'. allow(): `if self.spent() + self._reserved + worst > self.cap`.
- Fix: Add one Ledger method that, under the lock, appends the row and then drops the reservation (settle(worst, **row)). On exception, record a worst-case or 'unknown cost' row instead of only releasing. Take a file lock (fcntl) around allow and settle so separate processes share the guard.

## F7 MEDIUM: pipeline/oracle/run.py run_oracle (diff 2064-2099), run_day (2204-2215)
- Defect: When the corrective re-ask fails (vendor error, malformed reply or spend guard), the day keeps status OK and is reported NOT_AVAILABLE. - Fix: If the re-ask was issued and did not return a valid reply, mark the day NOT_MEASURED (retry failed / spend guard), or record a distinct availability such as 'NOT_AVAILABLE (first reply only; re-ask failed)' and exclude it from `measured`.

## Answers to the four questions

**(1) Can the guard skip a build that has something new to judge?**
Yes, in these identified paths: (a) routing mode / shadow state (RULING 86) not fingerprinted (F4) — a routing change or shadow-counter advance skips; (b) a pool moment lacking `video_id` — its newly-arrived pre-check answer is invisible (F5); (c) if `sp` at the end-fingerprint write is not the build's own final lock record, `open_work` undercounts (F3); (d) the vacuous-match risk (F11) is the *opposite* failure (never skips), but note the *converse*: if `build_inputs`' pool *doesn't* change from the first build's outputs while the *judgments* would (because the second build's stages read the new pre-check answers via the results dir, not via the pool), then... the fingerprint's `precheck_results` part *does* cover that — the second build's start fingerprint hashes the results dir, which now differs from... wait, the *end* fingerprint of build 1 also hashed the post-write results dir. So they match. Good — F11's risk is confined to the `moments` part. So: (a), (b), (c) are the skip-when-new paths.

**(2) Can a model call happen before it decides?**
The guard runs after `inputs.json` but also after `delivered_pins`, `build_inputs`, `with_variants`, `PS.ledger_entries`, `LB.rows/word_pass_index` — if any of these is model-backed, yes (F6). The test proves only "no router" (build_router→Built), not "no call"; the ruling demands "no router, no call, $0.00". Needs a one-line confirmation that all pre-guard reads are pure file/DB.

**(3) Is anything time-varying that keeps it from ever matching?**
`due` (minute-resolution via `now`) — but that's *intended* (a candidate coming due IS new work, pinned by test). `day_et` is day-quantized. `since`/`delivered`/`pins` are file-stable. The one *unintended* time-varying part: none found, **provided** the end-fingerprint's `now`-dependent parts (`due`) are computed with the same `now` as the next build would... they're not — the next build's `now` is later, so if any candidate's `until` falls between the builds, no match. That's intended-new-work. Also `os.path.getmtime` in `precheck_results` — **`getmtime` is time-varying!** Any *touch* (even a no-op rewrite, or an mtime-only change from a copy/rsync) of a results file changes the fingerprint even when content is identical. If the integrator rewrites result files idempotently (same bytes, new mtime), the guard never matches → the $0.00 guarantee silently defeated. **This is a real Q3 hit: [P1] — `precheck_results` hashes (name, size, mtime), not content; an idempotent rewrite (same bytes, new mtime) defeats the match.** Add to F5's family or standalone. The author even has `_file_sha` in scope and used it for spotlights/directives/scorer but *not* for the results dir. Strong P1.

## 3. NEW FINDINGS (cycle 2)

**N1 (P2, correctness-adjacent, nobody): the probe's `wait` can exceed the module's probe interval, silently serializing probes.** `wait = 60 + 15 = 75 s` (providers.json:84/92/101) while the module's probe interval is 120 s (`PROBE_EVERY_S`, downsignal.py:409) and SIGNAL_MODE_S is 30 s. Sequence: probe claims the slot at t=0, its threads hang, `run()` returns at t=75, `_report_probe` at the next tick (t≈80). Fine. But if the *next* `probe_due()` fires at t=30 (SIGNAL_MODE_S) while the first probe's threads still hang, `_probing()` returns True (the thread is alive) and no second probe starts — correct. The subtle part: a probe whose *report* is retained because the module didn't take it (downsignal.py:409-411) is kept only while `clock() - t < 120`; with the 75 s wait, a report retained at t=80 has 40 s of freshness left, and the next tick is 5 s later — it will be retried at t=85, then again... each retry consumes a tick but the *slot* was already spent at t=0. If the module keeps rejecting (its lock held by the builder's prober), the report is dropped at t=120+ and counted `probe_reports_lost`. All counted, all logged. **No defect; the margins are tight but sound.** I record it because the consensus's "the margins are tight but sound" (implicit) was never actually checked.

**N2 (P2, test-coverage gap, nobody): no test pins the probe's deadline against a *slow-but-answering* family.** The C1-1 test covers a *hanging* family (no answer ever); the C1-2 test covers a *dying* thread. But the amended rule's interesting boundary is a family that answers at 74.9 s — inside the 75 s wait — vs. one that answers at 75.1 s. In the first case the probe is answered with that family's time; in the second it's answered (if another family answered) but the slow family counts as not answered. Both are correct by construction, but nothing fails if someone later changes PROBE_WAIT_MARGIN_S to 0 (then a family answering exactly at its deadline races the join) or to 600 (the probe's report then lags the module's 120 s freshness window and every report whose module call fails once is dropped as stale — see N1's arithmetic: wait 615 > 120 means a retained report is *always* older than the freshness window, so `probe_reports_lost` becomes the steady state). That last case is a real latent trap: **PROBE_WAIT_MARGIN_S > ~45 s (120 − 60 − 15) would make the retained-report path systematically lose reports.** Today 15 s is fine. A one-line test (margin 600 → reports lost) would pin it. Nobody caught this; it's a P2.

**N3 (P2, observability, nobody): `snapshot()` reports `probe_families` but not the *computed* wait.** When someone edits a probe back-end's `timeout_s` to 300 (glm's main back-end already runs 300 s; the probe one is 60), the probe's wait becomes 315 s and N1's freshness arithmetic silently breaks. `probe_wait_s` next to `probe_families` (downsignal.py:523) would make that visible in live.json. One line.

**N4 (P3, style/robustness, nobody): `ask()`'s `except Exception` (downsignal.py:366-367) does not catch `BaseException`-level exits, but the C1-2 test uses SystemExit.** SystemExit *is* a BaseException, not an Exception — so how does the test pass? Because the *thread* dies, `outs[bid]` is never written, and the *fixed* `run()` reads by key-when-present (line 377-378: `outs[b] if b in outs else ... if a.is_alive() else (None, ...)`). So the (None, "its probe thread ended without an outcome") path is what handles SystemExit — the `except Exception` in `ask()` never fires for it. That's correct, but the *comment* on line 366 ("a family whose probe breaks was not asked") implies it catches the case the test exercises, when it's the *other* branch that does. Cosmetic; the behavior is right. (qwen's original framing — "if router.run raises... the ask thread dies silently" — was exactly this, and the fix went into `run()`, not `ask()`. Their diagnosis, the fix's location: both right, and the distinction matters.)

**N5 (verified, nobody): the amended `_flush` preserves the older-module path exactly.** Q3 of the reviewer's questions: with `note_family=False` (module's note() takes no `family`), the condition at line 325 (`p["fail"] is not None and self.note_family and p["families"]`) is False, so the else branch runs: `notes = [(True, answer, None), (False, fail, None)]` — precisely the old two-note sequence, and the `**({"family": fam} if fam else {})` at line 336-337 adds nothing when fam is None. With `note_family=True` but `families` empty (all failures from familyless back-ends), also the else: one failure note, no family kwarg. And `probe_kw` gains `families` only when the module's probe_due takes it (line 155-156). Verified: an older module gets exactly the old calls. This was the consensus's agreed item; I confirm it from the code, which nobody had done explicitly.

**N6 (verified, nobody): the drill note's `now` is the flush's clock, not the drill's.** downsignal.py:321: `self._call("note", False, now=_utc(self.clock()), ...)` — the drill count is noted at flush time, not at the time the drill call happened. For a drill this is recorded-never-counted, so the time is cosmetic. But it's the *only* note whose time is not the event's own time; if the module ever starts counting drills, the 5-s-flush lag (or longer, if the signal thread is busy) becomes a real skew. One-line fix: carry the drill's time in pending. P3.

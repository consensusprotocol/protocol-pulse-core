## 3. NEW FINDINGS FROM THIS REVIEW

Things the combined Cycle 1 analysis (mine included) still missed. I checked each against the code:

**N1 (P2) — A crash *inside* the calibration's rounds loop loses the answers already paid for, and the crash-path schedule can double past its evidence.** `flagcheck.calibrate` (flagcheck.py:294-301) runs `ex.map(one, todo)` inside a `with ThreadPoolExecutor(workers)`. If `one` raises (it catches only `AllBackendsFailed`; a `BackendError` escaping `router.run` is not possible, but any other exception — e.g. a `KeyboardInterrupt`-adjacent error, or a bug in `validator` construction — propagates), the `with` block exits, the executor shuts down, and *every* answered quote of that round is discarded; `_calibrate_checkers` then records a crash and nobody answers. That is fail-closed and correct, but note the cost: the round's spend is lost from the *record* (the attempts are still in the calls log via `on_attempt`, so the dollars are counted, only the calibration result is lost). Acceptable; worth one sentence in the design, not a change. — Actually, on closer reading: `one` catches `AllBackendsFailed` only; `router.run` can also raise... nothing else in the live path (it raises `AllBackendsFailed` after the chain, and `_try` converts everything else). So the only realistic raise is a programming error. Downgrade: N1 is a note, not a finding.

**N2 (P2) — The doubling schedule's "after the cap it starts again at 600" has a subtle interaction with the crash path: a *repeating* crash pattern (crash, crash, ...) never reaches the cap.** Trace: crash → `could = True` (cal is None) → if `check_recal_s` was 86400 (a previous pass) → 600; next crash → 1200 → 2400 → ... → 86400 → next crash → 600. So a permanently crashing calibration oscillates 600→86400→600→86400, i.e. it is retried 1+2+4+...+86400 ≈ 2×86400 s of waiting per ~2-day cycle — about 127 retries per 2 days, each costing 0 live calls (the crash may occur before or after the calls; if `watcher_checkers` raises *before* any call, the retries are free; if after, they cost). With the crash *after* the live calls (the realistic case — the calls succeed, the aggregation or kv write raises), each retry costs the full 32-call calibration: ~$0.003 × 127 ≈ $0.38 per 2 days. Bounded and small, but it is a *different* steady-state than the documented "a checker that keeps failing costs a few calibrations a day" (service.py:499-500 comment) — a permanently crashing calibration costs ~64/day, not "a few". The comment is slightly optimistic; the behaviour is bounded and cheap. P3, documentation.

**N3 (P2) — `check_once`'s `_check_seen` optimisation can skip a due retry by one loop, harmlessly.** service.py:536-539: `due = min(self.check_next.values(), default=inf)`; if the ledger is unchanged and `self.clock() < due`, return. A row's retry stamped `check_next[key] = clock() + 600` inside `check_row` (service.py:462-463) is picked up at the first loop after `due` — but the *calibration* path sets no `check_next`, so this is unaffected. No defect; noting it because the interaction of `_check_seen` with `check_next` was not explicitly reviewed: the guard `seen == self._check_seen` requires the ledger's (size, mtime) to be *identical*, and `check_row`'s own `_append` changes the mtime, so a completed check always clears the skip. Correct.

**N4 (P3) — The stored calibration's `asked_at`/`seconds` are written even on the crash path's *predecessor*... no: on crash, the kv is set to `{}` (service.py:510), losing the previous good calibration's record.** That is intended ("the stored calibration is emptied") and matches the consensus. But note the consequence: live.json's `second_model_checks_12h.calibration` goes to `null`→`{}` on a crash, so a dashboard reading it cannot distinguish "never calibrated" from "calibration crashed" — except via the `check_calibration_crash` event, which stats.live does not surface (stats.py:121-137 reads only `kind='flagcheck'` events and the kv). A crashed calibration is therefore invisible in live.json's second_model_checks block. P3: one line in stats.live (count the crash events in the 12 h window) would close it. Nobody caught this.

**N5 (P3) — `watcher_checkers`'s admission test uses `c["of"] == len(probes) and c["right"] == c["of"]` (flagcheck.py:341).** With `rounds=3`, a back-end that answers 15/16 in rounds 1-2 and the 16th in round 3 passes — correct. But a back-end that answers a quote *wrong* in round 1 and is never re-asked (it is not in `todo`) keeps that wrong answer — also correct (temperature 0). The subtlety: a back-end that answers the *same* quote differently across rounds cannot exist (only unanswered quotes are re-asked), so the "latest answer" concern from my Cycle 1 §1.1 is structurally impossible, not just avoided. Confirms the original design; no change.

**N6 (P2) — Interaction with the down signal: live calibration calls are now noted to the shared Heimdall state, and the calibration's 32 calls (2 back-ends × 16) at `workers=4`... wait, `watcher_checkers(router, workers=4)` (flagcheck.py:333) — the question asked in the diff's Q4.** Each calibration now makes 32 real calls (plus transport retries) through the router, so: (a) they are noted to the shared signal (downsignal.noted via `_on_attempt`, service.py:176-177) — 32 notes, each an flock'd write by the signal thread, batched via `pending` — fine; (b) they teach the *flagcheck* back-ends' breakers (glm53flash: 5 consecutive failures → open 300 s). During a Heimdall outage, the calibration's 16 questions × 2 back-ends, each with `attempts=2` and 3 transport retries, can record up to 128 failures — enough to open both flagcheck breakers, which then makes the *next* calibration's `router.effective(ROLE)`... no: `effective` does not consult the breaker (providers.py:799-804: frozen/enabled only); the breaker gates in `available()` (providers.py:806-818), which `run` consults. So a calibration during an outage gets `tried` entries of "skipped (circuit open)" → `AllBackendsFailed` → unanswered → rounds → still unanswered → `unmeasured` → the 600 s doubling. Correct, and the breaker's 300 s open window is shorter than the 600 s retry, so the next calibration finds the breaker half-open-able. Self-healing; no defect. But one *real* surprise: the calibration's failures also count toward the *spend meter's* `add_local` (providers.py:959-960) — negligible dollars, but the metered back-ends' reorder (providers.py:795-797) applies to the calibration's `router.effective(ROLE)` too, so while the meter is not 'ok' the calibration order flips. Both flagcheck back-ends are metered, so the flip is a no-op. No defect.

**N7 (P3) — `test_f1_a_calibration_an_outage_left_unanswered...` resets breaker state by hand (`for h in s.router.health.values(): h.open_until = 0.0`),** which is fixture knowledge, not production behaviour. Fine for a test; noted because the *production* path relies on the 300 s breaker window being shorter than the 600 s CHECK_RETRY_S — an invariant nobody wrote down. If someone later lowers CHECK_RETRY_S below the breaker's `open_s` (300), the doubling would fight the breaker. One comment line would pin it. P3.

**N8 (P2) — The rounds loop's `ThreadPoolExecutor(workers)` is created and destroyed per round.** With `rounds=3` and a fully-answering back-end, rounds 2 and 3 still construct an executor (round 2 runs the (empty) `todo`... no: `if not todo: break` (flagcheck.py:300-301) exits before constructing the next executor. Only *failing* rounds pay the cost. Correct as written; my initial reading missed the early break. Retracted.

So the genuinely new, actionable items: **N4 (crash invisible in live.json's second_model_checks block, P3)** and **N7 (the CHECK_RETRY_S > breaker open_s invariant is undocumented, P3)**. Everything else I chased down resolved to "correct as written" — which, at cycle 2 of a diff this size, is the expected outcome.

- **Rate limiting:** the design *is* a rate-limiting layer: per-back-end semaphore + global 20 (providers.py:769-771), shared throttle with Retry-After (:654-682), circuit breaker (:575-639), YouTubeGate for yt-dlp (watch.py:37-73). The A/B and flagcheck CLIs *add* their own inflight on top of the live watcher's (ab.py:252, flagcheck.py:577, 660-661) — documented as "the two together stay under ~20" (ab.py:417-418). That's a *convention*, not enforced: run the A/B with `--max-inflight 20` while the watcher is mining and you exceed 20 in flight at the gateway. Minor, documented, and the gateway (not this code) is the enforcement point. P3.
- **Secrets in code:** none. All keys via `key_env`/`key_env_prefix` (providers.json) → `Keyring` → env file. `providers.json` contains no secrets, only paths. ✓
- **Unvalidated input → FS/shell:** yt-dlp args are code-built (watch.py:129-130, fetch.py:92-93); video ids are regex-validated before path use (ledger.py:27, :100-101; purge.py:102-104; tools/ingest_watch.py:120). `overrides.json` is JSON-parsed and host-pinned. `_ids` (purge.py:107-120) extracts ids from *untrusted* delivery records but only accepts 11-char `[A-Za-z0-9_-]` matches. Prompt-injection: transcripts are fenced in `<sentences>` with a SECURITY note and `<>`→`‹` (mine.py:397-400, :104-110) — a real, tested mitigation (`test_untrusted_text_cannot_close_the_sentences_block`). ✓
- **One nit:** `Keyring` parsing (providers.py:184-200) strips quotes but not `export`-prefixed *values* with spaces, and doesn't handle `#` inline comments (`KEY=val # comment` → value `val # comment`). If the env file ever gains an inline comment, the key silently breaks (the back-end then reports `http_auth` — which *is* surfaced). P3.

## SECTION 4: FRONTEND QUALITY

There is no UI. The "frontend" is: `live.json`, the STATE notice line, coverage .md, and CLI stdout. Judged as such:

- **Loading/error/empty states:** the coverage report handles all three (empty → `coverage: null` → "unmeasured" string, coverage.py:110; error → `unmeasured_channels` table, :121-122; the missed table is the "loading→partial" case). `stats.write_live` is atomic (tmp+replace, stats.py:161-168). The STATE notice writers are idempotent and lock-protected (spend.py:35-63). ✓

The comment says "06:00 ET" — it's 06:00 ET only half the year. Cosmetic; the *behavior* (once a day, after 11:00 UTC) is unaffected. P3. Similarly `MAIN_TREE = "/home/ultron/protocol_pulse"` (config.py:14) and the many absolute paths in providers.json/purge.json — this is a single-machine deployment; `PP_INGEST_STORE`/`PP_SELECTID_PIPELINE`/`base_url_env` provide the escapes. Acceptable.
- **Mobile/JS:** N/A.
- **World-class?** For an ops artifact, yes: the coverage .md (coverage.py:111-124) names every missed video *with its reason*, the STATE line-1 protocol is genuinely well-designed (priority-ordered notices, each writer owns its lines, switch line always first), and `live.json` distinguishes measured from unmeasured everywhere. This is better than most production dashboards I review.

## SECTION 5: BACKEND QUALITY

- **DB writes:** single connection, `isolation_level=None` (autocommit) + `synchronous=FULL` + WAL (queue.py:82-88). Every write is a single statement; the RLock serializes. There's no explicit rollback because there are no multi-statement transactions — *except* `add_video` (:147-158) which is INSERT-then-conditional-event: if the process dies between, the event is lost but the row is there (the event is diagnostic, not state). Acceptable. The ledger append is the real transaction: flock + fsync + torn-tail sealing (ledger.py:45-66). ✓
- **External calls:** every provider call has a timeout (per-backend `timeout_s`, enforced in `_request` :351, Anthropic SDK `timeout=self.timeout` :400, Gemini `http_options` :448); retries are classified (RETRY vs not, providers.py:44-45) with backoff+Retry-After; the breaker and throttle degrade gracefully. yt-dlp: `timeout=120` (watch.py:59, fetch.py:93) — but note `gate.run`'s timeout applies to the *subprocess*; a hung yt-dlp at 120 s is killed by `config.ts()._ytdlp` (not shown, but the store's own). RSS: `timeout=15` (watch.py:88). ✓
- **Cron/loop failure:** `_loop` (service.py:823-832) catches `Exception`, logs, records an event, and *continues* — a poisoned loop (e.g. `watch_once` raising every time) still retries on schedule. `BaseException` (KeyboardInterrupt) propagates and kills the thread silently — but `run`'s stop path joins with timeout 30 (:877-878) and the process exits. The `fetch`/`mine`/`hook` loops additionally wrap their per-item work so one bad video doesn't kill the pass (service.py:249-261, :297-310, :462-469). ✓
- **Memory:** `_SHA` cache bounded at 4096 (purge.py:206, :219-220); `_conv` bounded at 5000 (service.py:689-690); `Health.events` is a 50-deque (providers.py:581); `check_next` grows with distinct moment ids — bounded by the 13 h ledger window, and entries are only *added* (never pruned) — at ~1,000 moments/day × 13 h ≈ 500-1,500 entries, each a small float. Fine. `route_heads` (downsignal.py:262) is drained on each tick. The one unbounded-ish thing: `attempts` list in ab.py/flagcheck CLIs (ab.py:253-259, flagcheck.py:580-588) — bounded by the run. ✓
- **Logging:** excellent. Every state change is an `events` row *and* a log line; errors carry `traceback.format_exc()[-2000:]` (service.py:255, :303, :419, :468, :529, :543); the calibration log line answers F1's "the log line must say live or replayed" — `_calibrate_checkers` says "asked live" (:570), `_reuse_calibration` says "calibration reused (asked live at ...)" (:601-603). Both. ✓. One gap: `_log` (service.py:182-189) writes to a file with no rotation — a weeks-long watcher's `service.log` grows unboundedly. At the observed verbosity (~1-5 lines/min) that's ~10-50 MB/week. P2.

## SECTION 6: WORLD-CLASS GAP ANALYSIS

**Already excellent (say so):**
- The failure-classification taxonomy (outage vs rejected, providers.py:39-70) and its consequences (no-try waits vs try-consuming retries, service.py:332-376) is the most rigorous "nothing lost" semantics I've seen in a pipeline of this size. Bloomberg-grade.
- The fail-closed discipline is *consistent* — zoneless times, unmeasured spend, unreadable optout, unreadable /proc, unreadable STATE — every one has a named, tested, non-guessing behavior. This is rare.
- The notice-protocol on STATE line 1 (priority, ownership, idempotence, switch-line-forever) is genuinely well-engineered.

**Material gaps:**

1. **No observability beyond logs.** There are no metrics (Prometheus/StatsD) and no structured trace of *latency distributions over time* — `live.json` has 24 h windows only. When the muse 502s caused the false plan_b, the diagnosis was forensic (reading logs + the shared state), not a dashboard. A 10-line `/metrics`-style snapshot (breaker states, throttle hits, calibration age, paid-route spend) would have made the 09:16 incident visible in one glance. This is the single biggest gap between this and a Coinbase-Advanced-grade operational posture. (P1, but it's *additive* — nothing is broken.)

2. **`service.log` unrotated** (service.py:106, :186-189). Weeks-long process, append-only. P2.

3. **The A/B's in-flight convention is unenforced** (ab.py:252, :417-418 vs the watcher's own 20). A coordinated run during a mining burst can exceed the gateway's goodwill. A shared file-based semaphore (the store already has `service.lock` precedent) would close it. P3.

4. **`check_next` never prunes** (service.py:139, :512-513, :527-528, :639). Bounded in practice by the 13 h window, but there's no mechanism, only arithmetic. One `dict` comprehension on read, or prune-on-read, would make it structural. P3.

5. **No integration test of the *full* restart→reuse→stale→recalibrate arc.** The tests cover each gate's mutation (per the change note) and the happy path, but not "reuse succeeds, then 24 h later the daily fires *while the stored record is still the reused one*" — i.e. that `check_calibrated = t.timestamp()` (the *live* start, not the restart) produces the intended "a day after the live one" and not "a day after the restart". Reading :599 + :613, it does — but this is exactly the kind of invariant that a time-travel test (fake clock) would pin. P2.

## SECTION 6: WORLD-CLASS GAP ANALYSIS

**Genuinely excellent (no change needed):**
- The outage-vs-rejection distinction (providers.py:62-70) with the "no try used" semantics (service.py:56-57, 327-371) is the best I've seen in a pipeline of this size — it's the difference between "the network hiccuped" and "the model returned garbage", and the state machine respects it.
- The reply cache keyed by (backend, model, prompt-sha, schema, max_tokens) (providers.py:906-908) — making retries and restarts free, and making the solo-prompt byte-identity (this diff's A37) a *correctness* property, not just an optimization. The diff's reliance on it (the "1 to 3" solo prompt) is exactly right.
- The fail-closed discipline is consistent: unmeasured → not-a-pass, everywhere (`is_conversation`, `expiry`, `CreditMeter.state`, `coverage.measured`, `flagcheck`'s unmeasured). No "assume yes" anywhere.
- The purge's "measured, never deleted" for out-of-scope media (purge.py:399-417) — most purge implementations silently eat things; this one reports.

**Material gaps:**

1. **No end-to-end latency SLO enforcement.** `stats.live` *measures* `publish_to_mined_min` (stats.py:76-78) but nothing *acts* on it. The design's promise ("never miss the most relevant content of the day", PBX 02:30) has no guardian: if `publish_to_mined_p90` drifts to 3 h, no notice fires, no STATE line, nothing. The coverage check catches *misses*, not *slowness*. A "p90 > 45 min → STATE notice" would close the loop. (The outage notice, service.py:730-756, covers only the total-outage case.)

2. **The `calls` table is the single source of truth for the paid-route cap, and it's lossy.** `Router._emit`'s `except Exception: pass` (providers.py:834-835) means a failed `q.call` insert loses the cost, and `RoleCaps`' loader (queue.py:183-187) reads only from `calls`. For a $2.00/day cap, losing $0.50 of accounting = 25% cap overrun. A periodic reconciliation (the replies_log JSONL, service.py:191-194, is a second, independent record) would make the cap trustworthy. Currently the two records can diverge silently.

3. **No backpressure signal to the *builder*.** The adapter (`best_unused_moments`) returns moments; the builder has no way to know "the ledger is 20 min behind" or "the hook pass is starving" (the `hook_due` newest-first policy, queue.py:201, means a burst of uploads starves the older ones until the burst passes — with `HOOK_VIDEOS=2` and 5 s loops, a 20-video burst takes ~50+ passes... each pass is a full hook+spotlight mine, minutes. A 20-video burst = hours of hook latency). The `hooks_12h` stat (stats.py:114-117) shows the *count*, not the *lag*. A `hook_lag_p50` would.

4. **`flagcheck`'s calibration is a crash-loop, not a start-time check** (see 1.1(o)). `check_roles` (service.py:84-89) was added precisely to prevent this class of bug for the *new* role — the same treatment for `flagcheck`/`probe`/`judge` (a `check_roles`-style existence+callable-verification at startup) would be consistent. Currently: `probe` is validated (providers.py:135-142), `flagcheck`/`judge` are not.

5. **The A/B's `<transcript>` prompt-injection gap** (ab.py:306, see 3) — the production prompts are hardened; the measurement tool that *decides the chain order* (§6: "the order is data: the A/B decides it") is not. If a transcript's `</transcript>`+instructions skewed the judge, the A/B would pick the wrong back-end. Low probability, but the A/B is the mechanism that migrates roles to the local model — its integrity matters.

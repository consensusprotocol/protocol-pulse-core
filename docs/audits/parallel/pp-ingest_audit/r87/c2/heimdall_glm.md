## 3. NEW FINDINGS (this cycle)

**N1 (new, P2): the probe's `probe_result` can be reported with a *stale* answered flag after a module failure, and the streak then counts a probe the module never recorded.** Trace: `_report_probe` (downsignal.py:223–238) calls `self._call("probe_result", answered, ...)`; if that call fails (HealthUnreadable, OSError), `_call` returns None, `_report_probe` keeps `self.last_probe` and the counts (`self.n["probes"] += 1`, `probe_answers += int(answered)`) — but the *outcome is discarded*: `probe_out` was already swapped out at the top of `_report_probe` (downsignal.py:224–225). There is no retry: the next tick's `_report_probe` finds `probe_out` None and returns. So a probe whose `probe_result` call failed is counted in `n["probes"]`/`n["probe_answers"]` (and shown in `last_probe`) but never recorded in the shared state — the module's `probe_streak` misses an answer it arguably earned. Compare the *notes* path, which does retry: `_flush` counts `unnoted` and the pending record is gone, but a note's loss is bounded (the next note supersedes it); a *probe* loss breaks the streak arithmetic — after 2 recorded answers + 1 lost answer, the module needs 2 more probes (2 more minutes) to come back, where the ruling's "3 answers in a row" arguably already happened. Impact: the BACK transition can be delayed by one probe interval per lost report, only while the shared state is unreadable — and while it is unreadable, nothing can transition anyway. So: self-limiting, but the asymmetry (notes counted as `unnoted` and effectively retried by the next note; probes counted as *delivered* when they were not) is a real, if small, accounting defect. Fix: on `_call` returning None in `_report_probe`, either put the outcome back (`with self.lock: self.probe_out = out`) or count it in a new `probe_reports_lost` bucket. Nobody caught this in Cycle 1 — qwen's #3 verified the AllBackendsFailed classification, glm's C1-3 fixed the *double* probe, but the *lost* report slipped past all three.

**N2 (new, P2): `_seen()`'s per-switch kv increments are not transactional with the evidence/event writes, and a crash mid-loop re-announces the *tail* of the batch — but the head-dedup only covers switches whose head is not None.** Working tree: for each unseen switch, the order is `write_switch_head` → `_evidence` → `q.event` → `kv_set(i+1)` (downsignal.py:269–282). A crash between the event and the kv_set re-announces that switch on restart: the head write is idempotent (C1-1), the evidence file gets a second "seen" line (append-only, harmless), the event duplicates (harmless). *But* for a switch where `head(rec, ...)` returns None (an unknown `to` value — downsignal.py:76–86 returns None for anything that is neither DOWN nor up), there is no head to dedup on, and the *log line* (downsignal.py:281) prints "an unknown switch: {json}" — a crash mid-batch would re-log it. All consequences are informational; the invariant that matters (the count) advances only after the writes. This is the same at-least-once shape the consensus already accepted for C1-1, extended to the evidence/event path; I record it because the consensus's C1-1 discussion treated the STATE head as the only duplicated artifact, and it is not. No change required; P3.

**N3 (new, P3): `head()`'s ET conversion uses `ZoneInfo("America/New_York")` at import; a switch record whose `utc` parses but whose zone-converted hour crosses a DST boundary is still correct — but the *module's own* `_prepend` (the builder's, not under review) uses `now.astimezone()` *local* time, so the two writers of "HH:MM ET" disagree when the host is not in ET.** Only our side writes to our STATE (A22: the module gets `state_md=None`), so the module's local-time habit never reaches our line 1. Verified: downsignal.py:41, 92 — `ET` is pinned, `t.astimezone(ET)`. Correct as built; the note is that A22 is what *makes* it correct, which strengthens the case for A22.

**N4 (new, P2, question 7): the probe cannot starve the miner, and the miner cannot starve the probe — verified, with one caveat worth recording.** The probe role's back-ends are dedicated (`heimdall_qwen27b_probe` / `heimdall_glm53flash_probe`, providers.json:78–94) with their own `max_inflight: 1`, their own `Health` and `Throttle` (Router.__init__ builds both per back-end, providers.py:704–705), and the *global* semaphore is 20 (providers.json:4) against a miner whose own back-ends cap at 12+8+4+4+4 = 32 theoretical — so the global cap of 20 is the only shared resource, and the probe's 1–2 in-flight calls cannot meaningfully crowd it. The reverse: the probe's `th.wait()` (providers.py:843) can sleep behind its own back-end's 429 backoff, but its Throttle is private, so only *probe* 429s delay *probes*. The caveat: the probe's 60 s timeout (providers.json:84, 92) is *longer* than the module's PROBE_EVERY_S (120 s) only by 2×, and a probe that hangs to its full 60 s on back-end 1 then fails over to back-end 2 for another 60 s occupies the signal thread's `_probing()` gate for up to ~120 s — exactly one probe interval. So the *next* probe_due (2 minutes later) can find the previous probe still in flight and skip; the probe cadence degrades to ~2× while a back-end hangs, which is precisely the behavior you want while it hangs. No defect; the arithmetic is tight by design and the tightness is documented (providers.json:111 "each back-end's 60 s deadline is the probe's"). What nobody said in Cycle 1: the *sum* of the two deadlines equals the probe interval, so a doubly-hanging probe exactly consumes its slot — worth knowing before anyone "fixes" the 60 s.

**N5 (new, P3): `stats.live`'s `signal` parameter is written into live.json but `cmd_status` (tools/ingest_watch.py:65–69) constructs no DownSignal, so `ingest_watch.py status` never shows the down-signal block.** The health loop's write (service.py:557–558) covers the operational read; the CLI's omission is a convenience gap, not a gap in the record. **N6 (new, P2, question 6): the health thread's read of `self.busy_since` / `self.error` / `self.error_since` is unsynchronized but safe — verified, and the *one* residual race is benign.** `check_notice` (downsignal.py:315) takes a four-attribute snapshot without the lock; the signal thread writes `busy_since` in `_call` (downsignal.py:178, 185) and `error`/`error_since` in `_fail`/`_recovered` (downsignal.py:291–292, 301). CPython's attribute reads/writes are atomic; the C1-2 fix guarantees `error_since` is never None while `error` is set *from the writer's side*, and the reader's `err_since if err_since is not None else now` (downsignal.py:317) covers the interleaving where it reads the new `error` and the old (None) `error_since` — the only window, one bytecode wide, and it yields `since = now`, i.e. the notice's "since" is the read time rather than the error time, off by the width of the window. Benign. The *stale* direction (old error, new since) cannot happen because the writer stores since first. This is exactly the discipline C1-2 installed; it holds.

**N7 (new, P3, question 3): `http_4xx` as "not answered" — yes, and here is the precise reason it is right.** A 400/422 is the gateway answering *this* request with "your request was wrong": the gateway is up. But the contract (the builder's, quoted) says "answered=True if it answered inside its deadline; False if it was down, refused, empty or late" — "refused" covers 4xx, and the ruling's signal is about the *gateway's* availability, where a 4xx storm is operationally the same as a refusal (the watcher's calls are not getting through). Also, decisively: the watcher's prompts are static and validated, so a 4xx here is far more likely a gateway-side regression (schema enforcement, model routing) than our bug — counting it as "not answered" makes the signal *more* sensitive, which is what a fail-safe wants. A23 is right. The one case that gives pause is 429: a rate-limited gateway is arguably "up", and a 429 storm would flip the signal to plan_b after 15 min even though the gateway answers. But under the 05:30 freeze the watcher's own 429s would be accompanied by the *builder's* 429s, and the ruling's Plan B (Grok, then any outside key) is exactly the right response to a Heimdall-wide rate limit. So 429-as-not-answered is also right, and for the better reason: the signal measures "can the fleet get through", not "is the process alive".

**N8 (new, P2, question 1, the consensus's own question): the ordering question resolves cleanly, and the answer is "no defect, by construction".** The concern: a pending answer flushed ~5 s late with its *own earlier* time can clear a failure the *builder's* process noted in between. Working through the module: our note(True, now=T0) arrives (wall-clock) at T0+5; the builder's note(False, T1) with T0 < T1 < T0+5 may have been applied first. The module's note() is order-of-arrival, not by timestamp: our late answer sets `failing_since = None` (the builder's module, note(): `s["failing_since_utc"] = _iso(now)` when answered), erasing the builder's failure clock. But the builder's *next* failure re-sets it, and the 15-minute rule needs 15 *continuous* minutes, so a 5-second-erased failure clock costs the builder at most 5 seconds of down-detection latency. Meanwhile the module's HEARTBEAT_S=30 dedup (its note(): `if answered and not drill and mono - _SEEN.get(path, -1e9) < HEARTBEAT_S: return`) means our frequent answers mostly don't even reach the state. The 15-minute rule is precisely the mechanism that makes 5-second-scale note-ordering noise irrelevant. Answer to question 1: not a defect; the design's margins (5 s flush, 30 s heartbeat, 15 min rule) are separated by 6× and 3× respectively, and each absorbs the one below it.

**N9 (new, P3, question 2): two processes probing — the race is real, the consequence is one extra probe, and the *fix* belongs on neither side.** Both the watcher and the builder can see `probe_due() == True` simultaneously (the module's probe_due does not claim; the contract gives no claim primitive), both call their back-ends, both report `probe_result(True)`. The module's `probe_streak` then increments twice for one *round* of probes — so "3 answers in a row" can be 2 rounds. Does it matter? The streak's purpose is "3 consecutive successful probes prove Heimdall is back"; two answers from two *different processes' probes* are *more* independent evidence than three from one, not less. The BACK transition fires one round early, on stronger evidence. Also: while in plan_b, `probe_due` returns True whenever `last_probe_utc` is 120 s stale, and each process's own probe stamps it, so the two processes *self-serialize* through the shared `last_probe_utc` — the race window is only the sub-second overlap of two concurrent probe_due reads. Answer: the module's (the contract's) — it owns the streak semantics — and the semantics are *fine*; a claim primitive would add a failure mode (a crashed claimer) to save one redundant probe. Whose side: neither; leave it.

2. **D3/N6 — `Overrides.get` runs `on_change` (a SQLite event + a log append) inside its lock, on the calling thread** (providers.py:527–544; service.py:173–178; reached from every `OpenAICompatBackend.base` read at providers.py:320 and from `DownSignal._drill` at downsignal.py:139–140, 156). Fix if desired: move the `on_change` call outside the lock (swap-then-notify). Cost when unfixed: a slow log briefly serializes base-URL reads across all in-flight requests; `_emit`'s swallow (providers.py:763–768) means it can never fail a call. Latency, not correctness.
3. **N11 — the drill counters' semantics differ** (downsignal.py:106, 131 vs the module's `drills`): our `pending["drills"]` counts outcomes, the module's counts notes (one note per 5 s window). Informational; a one-line comment would prevent the eventual confusion.

**P3 (record, do not fix):** N2 (at-least-once evidence/event duplicates on a mid-batch crash — same shape the consensus accepted for C1-1); N5 (`ingest_watch.py status` shows no down_signal block); N7/N8/N9/N12 (the questions' answers: 4xx-as-not-answered is right; the 5 s/30 s/15 min margins absorb the note-ordering noise; the two-process probe race costs one redundant probe and *adds* independence; empty-both-families resetting the streak is consistent with A23).

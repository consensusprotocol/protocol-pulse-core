## 3. NEW FINDINGS (cycle 2)

**N1 (P2, correctness, nobody): the hook pass's `tries` accounting conflates outage passes with rejected passes, and the outage path burns the retry budget.** service.py:354: `tries = int(v.get("hook_tries") or 0) + (1 if rejected else 0)`. Then service.py:359: `if failed and tries < HOOK_TRIES`. Consider: pass 1 = pure outage (rejected=0, tries=0), pass 2 = pure outage (tries=0), pass 3 = one rejected window (tries=1). Now `tries` is 1, and the video needs *two more* rejected passes before the good windows' hooks are written — but the *outage* passes, which the module docstring says "use no try" (service.py:16-17), correctly added nothing. That part is right. The subtle case: pass 1 = outage, pass 2 = rejected (tries=1), pass 3 = outage (tries=1), pass 4 = rejected (tries=2), pass 5 = rejected (tries=3) → good windows written. Fine. But now: pass 1 = *mixed* (2 outage windows + 1 rejected window). `rejected` is non-empty → tries=1. The outage windows' failure consumed a try *because a different window was rejected*. Is that wrong? The moment pass (service.py:287) has the identical rule (`passes = mine_tries + (1 if rejected else 0)`), so it's consistent — but the *rationale* differs: for the moment pass, MINE_CONTENT_PASSES=3 bounds *rejected* passes because cached replies make retries free; for the hook pass, HOOK_TRIES=3 bounds the same. Consistent, defensible, and the outage-retry loop (HOOK_RETRY_S=600) is unbounded in count but bounded by the 12 h horizon. **Verdict: not a bug, but the interaction deserves a test** — a video that oscillates outage/rejected never writes its good windows until 3 *rejected* passes accumulate, and the 12 h horizon can expire first. At HOOK_RETRY_S=600, 3 rejected passes need ≥2 failures×600 s = 20 min minimum; the horizon is 12 h. Safe. P3, note only.

**N2 (P2, nobody): `hook_video`'s crash handler can leave `hook_next_ts` at its *old* value while `hook_ts` stays NULL, and the crash note overwrites the outage note — but worse, a crash *after* `self._append(v, lines)` (service.py:365) but *before* `set_hook(hook_ts=...)` (service.py:366) writes the rows twice on the next pass.** Trace: `_append` succeeds (rows in the ledger, fsynced), then the process dies (or `set_hook` raises — it's a plain UPDATE, but the SQLite connection is shared under `q.lock`, so a lock timeout raises `sqlite3.OperationalError`). Next pass: `hook_due` still selects the video (hook_ts IS NULL), the hook question runs again — but the replies are *cached* (prompt+schema+max_tokens+backend key, providers.py:776-778), so the second pass's `mine_video` returns the *same* lines, and `_append` writes them *again*. The ledger now holds two identical lines for the same moment_id. Is that harmful? The adapter's `latest` dict (ledger.py:274-278) dedupes by moment_id — the latest wins, and since the lines are identical, no harm. `carry_forward` also dedupes by moment_id. And `observations` would be 1 in both copies (each pass's own count). So: **benign duplication, absorbed by the latest-wins read.** But it's worth noting that the *cost* doubles in the `calls` table (the cache makes the second pass's calls cost $0.00 — `cost_usd: 0.0` in the cache-emit, providers.py:793 — so no, the cost does NOT double; the cached read emits kind="cache" with cost 0). **Verdict: benign, by design, and the design holds.** Nobody said this; it's the kind of thing a cycle-2 review should *prove* rather than assume. P3, documented.

**N3 (P2, nobody): the hook pass's eligibility role "hook" is judged against the *builder's* registry semantics, but the hook pass runs on videos whose channel may have been *removed from the registry* between the moment pass and the hook pass — and `hook_video` handles that (service.py:342-344, `chan is None` → hook_ts set, 0 rows, "channel opted out or not watched").** Correct. But the *moment* pass's equivalent (service.py:233-237) sets the *video's state* to OPTOUT, while the hook pass only sets hook columns — so a video whose channel vanished after MINED stays MINED with hook_ts set, and `hook_due` never selects it again. Consistent. However: if the channel is *re-added* later, the video is MINED with hook_ts set and never re-hooked — its 12 h window has almost certainly passed anyway. Benign. P3.

**N4 (P1, nobody — the one real new finding): `hook_once`'s `free` computation races with itself across loop iterations, and the `HOOK_VIDEOS * 2` over-fetch in `hook_due` (service.py:391) can starve the *newest* videos.** Trace: `hook_due(HOOK_HORIZON_S, HOOK_VIDEOS * 2)` returns up to 4 videos, newest first. The loop claims until `len(hook_inflight) >= HOOK_VIDEOS` (2). Suppose 3 videos are due: v1 (newest), v2, v3. First iteration: v1, v2 claimed, inflight=2. v3 skipped. Now suppose v1's pass finishes *between* the `hook_due` call and the loop reaching v3 — no, the loop is synchronous; v3 is skipped this iteration and picked up 5 s later. Fine. But: suppose v1 and v2 are *both* still in flight from the previous iteration (inflight=2), `free=0`, return 0 — correct. Now the subtle one: `hook_due`'s LIMIT is `HOOK_VIDEOS * 2 = 4`, but the loop skips videos already in `hook_inflight` *before* checking the cap. If 2 videos are in flight and 4 are due, the loop iterates: v1 (in flight, skip), v2 (in flight, skip), v3 (claim, inflight=3? No — the cap check `len(hook_inflight) >= HOOK_VIDEOS` → 2 >= 2 → skip). So v3, v4 never claimed this iteration. Correct. **But if the two in-flight videos are *old* (v1, v2 from the previous cycle) and v3, v4 are newer, the over-fetch of 4 is exactly consumed by the 2 skips + 2 cap — the newest are still reached.** Actually, wait: the *order* is newest-first, so the 2 in-flight are the *newest* from the previous iteration. If a *new* video published since then is now newest, it's v1 in this iteration's results, not in flight, claimed. Fine. **Verdict: correct, but the `HOOK_VIDEOS * 2` constant is load-bearing in a way nobody documented** — it must be ≥ HOOK_VIDEOS (the cap) + the number possibly in flight (≤ HOOK_VIDEOS) for the newest to always be reachable. 2+2=4. Exactly. If HOOK_VIDEOS were 3, `*2` = 6 ≥ 3+3. Holds. P3, note the invariant.

**N5 (P2, nobody): `cmd_hooks` (tools/ingest_watch.py:151-164) constructs a `Q.Queue` without the service's clock, so its `since` uses `time.time()` while the service's `hook_due` uses `self.clock` — in tests these differ, in production they're the same.** Cosmetic. **N6 (P2, nobody — worth fixing): the `hook` role's `attempts: 3` (providers.json:83) interacts with the *router's* per-attempt rejection-retry, so one window's hook question can cost 3× the model calls before the *pass* counts it as rejected — and HOOK_TRIES=3 passes × 3 attempts = up to 9 model calls per window before the good windows' hooks are written.** The moment role has the same shape (3×3=9), so it's consistent, but the hook pass runs over *every* mined video in the 12 h window — the cost multiplier is the population, not the shape. At the measured $0.0008/window (providers.json:23), 9 calls × 201 videos × ~10 windows ≈ $14.5 — well under the $460 cap. Fine. P3, note only.

**N7 (P1, nobody — the strongest new finding): the hook pass's *dropped* accounting (mine.py:431-441) runs AFTER the in-pass dedupe, so a range seen in two windows where one observation's duration is measured and the other's is not keeps the *line's* duration — which is the FIRST observation's (mine.py:426-429: `by_range[key] = line` only on first sight; the second observation raises `observations` and merges flags but never re-derives duration).** Is that right? The duration is a function of (w0, w1) and the record's tokens — *not* of the observation. **N8 (P2, nobody): `stats.live`'s `hooks_12h` (stats.py:108-113) uses `SUM(hook_ts IS NOT NULL) AS done` — in SQLite, `SUM` of a boolean expression returns the count of truths, but if ALL rows have hook_ts NULL, `SUM` returns NULL, and `hk["done"] or 0` handles it. Correct. But `SUM(COALESCE(hook_rows,0))` over zero rows returns NULL → `rows_ or 0` → 0. Correct. And `COUNT(*)` over zero rows returns 0, not NULL. Correct.** All three aggregates are NULL-safe. Nobody checked; I did. P3.

**N9 (P1, nobody — this one is real): the hook pass's `_append` (service.py:265-274) computes `since` from `v.get("discovered_ts")` — but the *hook* pass's earlier lines may have been written by a *previous* service run whose `discovered_ts`-minus-86400 cutoff... no, wait.** `discovered_ts` is a property of the video, not the pass. The cutoff is `discovered_ts - 86400` (one day before discovery), and the docstring says "its lines cannot be older" (service.py:277-278). Is that true for the *hook* pass? A hook line's `mined.at` is the hook pass's time, which is ≥ the video's discovery. So yes, all the video's lines (moment AND hook) are ≥ discovered_ts > discovered_ts - 86400. **But** — and here's the subtlety — `ledger.read(path, from_time=since)` uses `offset_before` (ledger.py:122-149), which *bisects* on `mined.at` and then skips a partial line. The bisection assumes lines are in mined.at order (the service stamps them under the append lock, ledger.py:49-52). The hook pass and the moment pass both stamp with `config.iso` — *the same function, called at append time*. So the file IS in mined.at order across both passes. **But the *stamp* is taken once per append** (ledger.py:50: `at = stamp()`), so all lines of one append share one timestamp — and the moment pass's append and the hook pass's append are serialized by `wlock`, so their stamps are ordered. Within one append, all lines share the stamp. So the file's mined.at order is: [moment-pass lines at T1] [hook-pass lines at T2] [re-mine lines at T3], T1 < T2 < T3. Monotonic. **The bisection is sound.** However: the *hook* pass's lines for a video carry `mined.at = T2`, and the *moment* pass's lines for the SAME video carry T1 < T2. `video_lines(path, vid, since=T1-1day)` reads from the bisection point — which is at or before T1-1day, so it catches both. Correct. **Verdict: sound, and the one-day margin (service.py:271) covers the documented "at most one mining pass (minutes) out of order" (ledger.py:126-128).** Nobody traced this; the hook pass's interleaving with the moment pass is exactly the case the margin was designed for. P3, documented — but it's the kind of thing that deserves a test: a hook line appended *between* two moment lines of the same video, then a `video_lines` read.

**N10 (P2, nobody): the `dropped_s` report field (mine.py:439) is a list of floats appended via `report.setdefault("dropped_s", []).append(d)` — but `report` is also serialized into the `hooks` event (service.py:369-370: `dropped=rep["dropped"]`), which does NOT include `dropped_s`.** So the event loses the lengths; only the log line (service.py:356-357) carries them.

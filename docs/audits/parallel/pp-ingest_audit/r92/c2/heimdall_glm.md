## 1. WHAT DID THEY CATCH THAT I MISSED?

**Muse's TOCTOU on `--rerun` (ingest_watch.py:157-160) — I called the rerun "correct, idempotent" and stopped.** Muse is right that the UPDATE races the watcher's hook loop, and I under-verified the consequence. Working it through: the CLI resets `hook_ts=NULL` on a video the watcher has already claimed into `hook_video` (service.py:337). That pass finishes, `set_hook(hook_ts=...)` writes its result (service.py:380), and the row now has `hook_ts` set but `hook_note='re-run: mine-hook/2'` — so the *next* `--rerun`'s guard `(hook_note IS NULL OR hook_note <> 're-run: ...')` (ingest_watch.py:158) skips it. The video is silently never re-run under the new question despite the operator asking. Also, the in-flight pass mined under the *old* prompt (its rows carry `prompt_version: mine-hook/1` in `mined`), so the ledger holds old-question rows the rerun was meant to replace. Muse's "wasteful, not data-loss" is right in direction but understates it: the failure mode is *stale rows that look current*, because `hook_rows`/`hook_cost_usd` are overwritten by the in-flight pass while the note says "re-run". The help text (ingest_watch.py:225-228) does say "run it while no hook pass is in flight", so the code documents the race rather than fixing it — defensible, but the second-`--rerun`-recovers claim in the help is only true when the first rerun's pass actually completed.

**Qwen's ledger-lock analysis — partially new to me.** I verified `carry_forward` + `append` under `wlock` (service.py:284-286) but did not note that `check_row` (service.py:441-442) builds its new line by `json.loads(json.dumps(l))` of a line read *outside* the wlock and then appends. Two checkers appending different moments is serialized by wlock; a checker and a hook pass appending the *same* moment_id (a hook row for a moment that also gets a flagcheck) is also serialized, and `carry_forward` re-reads under the lock, so the later line carries the earlier's flags. I traced it: no lost update. Qwen's "the real bug" hunt ends inconclusively (their output is truncated mid-sentence); what is there, I disagree with — the flock-vs-wlock layering is sound because wlock strictly nests the flock within this process, and the only other writer (a manual `flagcheck` run) is fail-closed on the torn-tail check.

**The consensus's measured refutation of my C1.** This is the most important correction to my Cycle 1. I hedged: "probably correct, unverifiable from the provided code." The consensus *measured* it: `canon.canon_tokens(heads=True)` drops the marker in both forms, 229 ledger texts begin with `>>`, and the pinned test `test_a_leading_speaker_marker_never_hides_the_first_word` exists. My "unverifiable" was wrong — it was verifiable, and was verified. Lesson recorded: when the prompt says a test compares the sets with the builder's source, the verification obligation is discharged by reading the test, not by pleading the module's absence.

**Muse's `minutes: 0.0` vs `None` nit (mine.py:248-252).** I noted the `or 0` → 0.0 → `turns_per_min: None` subtlety and called it "fail-soft, informational". Muse wanted `minutes: None` when timing is missing. Partially agree: for a record whose *last* segment lacks `end`, `minutes: 0.0` with `speaker_markers: N` is indeed misleading (N markers in 0.0 minutes), but the `measured_from` field and the `turns_per_min: None` already say "the timing half failed". The implemented fix (consensus: `measured_from: "no segments"`, minutes None for the empty record) covers the case that actually occurs. Residual: a record whose *final* segment has `end: null` still reports `minutes: 0.0`. Nobody pinned a test for that; it remains a P3.

## 3. NEW FINDINGS (this cycle)

**N1 (P2, new — nobody caught it): the rerun's note-guard permanently skips videos whose hook pass *failed* rather than succeeded, in a specific interleaving.** Trace: video V is mined, hook pass runs, fails on an outage → `set_hook(hook_next_ts=..., hook_note="OUTAGE: ...")` (service.py:372-374), `hook_ts` stays NULL. Operator runs `--rerun`: the UPDATE (ingest_watch.py:157-160) matches V (note ≠ 're-run:...'), sets `hook_note='re-run: mine-hook/2'`, `hook_ts` stays NULL. Good — V is due again. Now suppose the re-run pass *also* fails: `set_hook(hook_next_ts=..., hook_note="OUTAGE: ...")` **overwrites the 're-run:' note** (service.py:372-374 writes hook_note unconditionally). A second `--rerun` now matches V again (note ≠ 're-run:...') — correct, it should. But if the re-run pass *succeeds*, `set_hook(hook_ts=..., hook_note=None)` (service.py:380-382) clears the note — and a *third* `--rerun` (a later prompt version, say mine-hook/3) matches it. That is all correct. The actual gap: **the guard keys on `hook_note`, but `hook_note` is also the failure-reason field.** A video that was re-run, then failed, then succeeded, then failed again, ends with note = failure text and `hook_ts` set — a *fourth* `--rerun` with the *same* version re-queues it (note ≠ 're-run:...'), spending another full pass on a video that already has current-version rows. Cost, not correctness: each pass is ~$0.001-0.01 and the rows are deduped. Downgrade to P3. What *is* P2: the help's promise "a video whose re-run pass has not succeeded is queued again by a second --rerun" (ingest_watch.py:226-227) holds only because failures overwrite the note — which is the same mechanism that makes same-version re-queues overspend. The two behaviours share one cause; the help documents the helpful half.

**N2 (P3, new): `stats.rows_by_episode` counts a video's hook_rows under its *final* measure, but the measure is written only on success.** service.py:378-379 writes `episode_markers`/`episode_tpm` in the success branch only; the failure branch (service.py:372-374) does not. Correct as written; but the *rerun* path resets `hook_ts=NULL` while leaving `episode_markers`/`episode_tpm` from the previous successful pass (ingest_watch.py:157-160 does not clear them) — so between the rerun UPDATE and the new pass's success, `rows_by_episode` (stats.py:115-119, which requires `hook_ts IS NOT NULL`) correctly excludes the video, and after the new success the measure is overwritten. No stale-read window. Verified: no bug, but only because the stats query filters on `hook_ts IS NOT NULL`. Had that filter been forgotten, the rerun would have shown stale measures. Fragile-by-accident, correct.

**N3 (P3, new): `episode_measure`'s marker count double-counts a segment whose text is exactly `&gt;&gt;`... no — verified single.** `TURN_MARK = re.compile(r">>|&gt;&gt;")` (mine.py:235): on the string `&gt;&gt;`, `findall` matches once (the alternation's first branch `>>` does not occur — the literal is `&gt;` + `&gt;`, no bare `>>`... actually `&gt;&gt;` *contains* `>>`? No: the characters are `&`, `g`, `t`, `;` — the substring `>>` does not occur. Wait: `&gt;&gt;` = `& g t ; & g t ;`. No `>>` substring. Correct, one match via the second branch. But a segment `&gt;&gt; >>` (escaped then raw, which happens when a caption mixes conventions) matches twice — which is *correct*, two markers. And a segment `&gt;` alone (a lone escaped `>`, which YouTube produces) matches zero — correct. One more: the regex alternation is ordered `>>|&gt;&gt;`; on `&gt;&gt;` the first branch fails at position 0 (`&`), the second matches. On a hypothetical `&gt>>`... not a YouTube form. **Verified: the count is right for every form I can construct.** This closes my Cycle 1 1.1 first bullet more firmly than I did.

**N4 (P3, new): the hook prompt's `@@PRONOUNS@@` substitution leaks the sets into the prompt in sorted order, which is *not* the builder's order — cosmetic, but the test `test_the_opener_words_are_the_builders_verbatim` (per the consensus) compares the *sets* via ast, so the prompt's presentation order is unconstrained.** No action.

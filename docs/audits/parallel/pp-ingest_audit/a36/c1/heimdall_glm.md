### 1.1 The change under review: `is_conversation` (mine.py:302-315)

The predicate:


Verified against the ruling's four cases:

| Input | `n` | `t` | Result | Ruling says |
|---|---|---|---|---|
| marked, 0.29 tpm | 5 | 0.29 | `False` (skip) | skip ✓ |
| marked, 0.3 tpm | 5 | 0.3 | `True` (ask) | ">= 0.3" → ask ✓ |
| no markers | 0 | 0.0 | `True` (ask) | ask ✓ |

| `None` / `{}` | None | None | `True` (ask) | ask ✓ |

The predicate is correct. One subtlety worth noting: `isinstance(n, bool)` is checked **before** `isinstance(n, int)`, which is required because `bool` is a subclass of `int` in Python — `isinstance(True, int)` is `True`. The order matters and is right. Same for `t`. This is the kind of thing that usually gets missed; it didn't.

**Boundary check**: `t >= 0.3` with `t=0.3` exactly → asked. The ruling says ">= 0.3" — matches. The test at test_mine.py param case `({"speaker_markers": 5, "turns_per_min": 0.3}, True)` covers it. Good.

**Float equality caveat**: `mine.episode_measure` (mine.py:353-354) rounds `turns_per_min` to 2 decimals: `round(n / mins, 2)`. So a true rate of 0.2999 rounds to 0.3 and is asked; a true 0.2949 rounds to 0.29 and is skipped. This rounding happens *before* the comparison, so the predicate compares the rounded value against 0.3. This is defensible (the ruling's 0.3 is itself a 1-decimal number) but it means the effective boundary is [0.295, 0.305) → 0.3. Not a bug; a documented-in-advance rounding. No test covers the 0.295→0.3 rounding boundary, but the effect is one video's worth of $0.006. Immaterial.

### 1.8 Edge cases that will break

**`episode_measure` with a single segment** (mine.py:350): `mins = (segs[-1].end - segs[0].start)/60` — with one segment, that's its own duration. If it's 0 (a 0-length segment), `mins=0` → `turns_per_min=None` → asked. Fine.

**`_mmss` with negative/None** (mine.py:358-363): handled.

**`windows()` with one huge sentence** (mine.py:371-389): `j > i and words + n > max_words` — the first sentence is always taken even if over budget (j==i skips the check). Then `i = max(j - min(overlap, (j-i)//2), i+1)`. With j-i==1: `min(6, 0)=0` → `i = max(j-0, i+1) = j` — wait, `j - 0 = j`, and `i+1 = i+1`; since j = i+1, both are i+1. So i advances by 1. ✓ (the "never walk one sentence at a time" test covers the general case; the huge-sentence case advances 1/window by necessity).

**`hook_due` with `published_ts` NULL**: `published_ts >= ?` — NULL >= x is NULL → row excluded. But a MINED video always has published_ts (fetch.py:169-172 refuses to progress past PROBE_RETRY without one... wait, actually: `if pub_ts is None: PROBE_RETRY` at fetch.py:169-172, so a TRANSCRIBED→MINED video always has it). ✓.

**`is_conversation` with `episode` being a non-dict** (e.g., a list): `ep = episode or {}` then `ep.get(...)` → AttributeError on a list. Only `None`/dict/`{}` are ever passed (mine.py:575-576, service.py:405). The test passes `None` and `{}`. A list would crash — but nothing produces one. Immaterial.

**`stats.py` `hk["asked"]`**: `SUM(spot_rows IS NOT NULL)` — in SQLite, `SUM` of 1/0 integers. If *all* rows have `spot_rows` NULL, `SUM` returns... SUM of no rows is NULL, but here it's SUM over the group's rows of a 0/1 expression — if there are rows, it's an integer; if the WHERE matches no rows, the whole `q.rows(...)[0]` returns one row with `COUNT(*)=0` and `SUM(...)=NULL` → `hk["asked"] or 0` → 0. ✓ (the `or 0` guards).

**`_route_tick` when `self.view` is stale**: `v = self.view if not self.error else None` (downsignal.py:207). If the last successful `_seen` was 10 min ago and the state file since became unreadable, `self.error` is set (by `_call` failing, or by `_seen`'s except) → `v=None` → route closes... no: `if v is None: paid_open=False, route_why=...; return` (downsignal.py:209-211). So a transient unreadable state *closes* the paid route (paid_open=False) — meaning the miner switches back to the Heimdall-only chain while the signal is unreadable. Is that right? The design says "A signal not read opens, closes and spends nothing (paid_open False...)" (downsignal.py:201-202) — yes, documented. But note: if the route was *open* (mining on Grok) and the signal goes unreadable, the route closes and the miner waits on Heimdall — even though Heimdall is (probably) still down. The videos then wait in the queue. That's the documented fail-closed behavior. It costs: during a signal outage, new uploads stop being mined on the paid route.

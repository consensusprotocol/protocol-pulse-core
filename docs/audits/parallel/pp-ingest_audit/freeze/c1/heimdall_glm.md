**C1. `mine_once` releases the router while other videos may still be mining (race).**
`service.py:283-285`: `if free == 3 and not self.q.due(Q.MINE_DUE, 1): self.router.release()`. `free` is read under `self.ilock`, but the check-then-release is not atomic with respect to the *other* mine-loop iteration — actually there is only one mine loop thread, so `mine_once` itself is serialized. However, `mine_once(wait=False)` submits to `self.videos` (3 workers) and returns; the *next* `mine_once` 5 s later sees `free = 3 - len(self.inflight)`. `inflight` is discarded in `mine_video`'s `finally` (service.py:233-235) — but that runs on the *worker* thread, while `mine_once` reads it under `ilock` on the loop thread. That part is fine. The real race: `router.release()` (service.py:284) calls `OllamaLocalBackend.release()` (providers.py:478-482) which takes `_llm_lock` and sets `self._llm = None` while a *concurrent* `complete()` (providers.py:463-466) may have just grabbed `llm` under the lock and be calling `llm._post(...)` at providers.py:469 *after* `release()` already called `llm.stop()`. Sequence: thread A enters `complete`, takes `_llm_lock`, gets `llm`, releases the lock, starts `llm._post`; thread B (release) takes the lock, sees `self._llm` non-None, calls `llm.stop()`; A's `_post` now runs on a stopped model. Whether that raises depends on `LocalLLM` (not shown), but the code comment at providers.py:470 ("a GPU0 stop (BaseException) is never renamed: it propagates") shows the author expects exactly this. The `mine_once` guard (`free == 3`) makes it *unlikely* but not impossible: `inflight` is discarded in the `finally` of `mine_video` (service.py:233-235) *before* the worker thread finishes returning, and `mine_once`'s `free == 3` check happens on the loop thread — there is a window where `inflight` is empty but the last worker's `mine_video` has not yet returned from `_settle`... actually no: `finally` runs after `_settle`. But `mine_once(wait=False)` returns after *submitting*; the loop's next iteration 5 s later can see `free == 3` while a just-submitted future has not yet added to `inflight`? No — `inflight.add` happens synchronously in `mine_once` (service.py:289-290) before submit. So the residual race is only the release-vs-`_post` one above, plus: `mine_once` computes `free` then calls `self.q.due(Q.MINE_DUE, 1)` *outside* the lock (service.py:283) — benign. Verdict: **low-probability race, real**. Also note `close()` (service.py:101-108) calls `router.release()` while `run()`'s threads may still be finishing (they are joined with 30 s timeout at service.py:358-359, then `close()` — a wedged `mine_video` past 30 s loses).

**C2. `_settle`'s partial-branch can silently skip appending forever.**
`service.py:256-258`: `if not was_partial or len(failed) < int(v.get("windows_failed") or 10 ** 6): ledger.append(...)`. Consider: pass 1, 2 windows fail (rejected×3) → MINED_PARTIAL, `windows_failed=2`, lines appended. Retry: 2 windows fail again, `len(failed) == 2`, not `< 2` → **no append**. Correct, nothing changed. But now consider the *good* case: pass 1 fails 2 windows, appends 5 lines. Retry mines one of them: `failed=1 < 2` → append. Good. Now the subtle one: retry mines *the same* windows but the model returns *different/extra* moments (temperature 0, but a different back-end after a freeze lift, or a cache miss). `len(failed) == 2`, not `< 2` → the new moments are **never appended**, yet `moments=len(lines)` (service.py:261) overwrites the row's count with the new, unappended count. The ledger and the queue row now disagree, and the coverage/adapter never see the new lines. This is a genuine correctness bug in the "retried until 72 h" promise (design §7: "its later lines appended only when a retry mines more windows" — the code interprets "more windows" as *fewer failures*, not *more/different moments*).
